### C-1.8.2-020 (S-1.8.2-003, F03): auto sync falls back to a full refresh when content changed

**What**: After a first sync, `--mode auto` no longer settles for deletions only. If SourceMember reports any added or modified member, or a change of a type sfgraph cannot map, the same run does a full refresh. The result's `mode` is `full` and `warnings` has `incremental:fellBackToFull:changed=N`. A modified Apex class gets its new body and hash. No changes, or only deletions, keep the incremental path.

**How**: `packages/core/src/ingest/live-ingest.ts` (mode selection, around lines 714-750): in auto with source tracking and a prior sync, a pre-scan reads SourceMember through `iterChanges`, and the changes are reused by the incremental branch so the table is queried once. A full run advances the watermark as any full sync does (`markSyncComplete`, around line 2200). Deletions seen by the pre-scan are applied at the start of the fallback full run (via `processOne`, the same path incremental uses), because a full run without `--detect-deletions` would otherwise leave them in the graph while the watermark moves past them.

**Check**: `pnpm build && pnpm --filter @ryanstark24/sfgraph-core exec vitest run src/ingest/__tests__/live-ingest.incremental-fallback.test.ts`. Expect 6 passed. "a deletion seen alongside a modification is still applied in the fallback full run" (one deleted and one modified class under auto, detectDeletions unset: the deleted node is gone, the modified one has a new hash) fails without the apply-deletions loop. The tests "a modified Apex class under auto gets its new body and hash" and "pure deletions and no changes keep the incremental path" cover this claim. With the source changes stashed, 3 of the original 5 fail (the two others pin behaviour that is kept).

**Test timing**: the core test file calls `limiter.incrementReservoir` and `metadataPool.incrementReservoir` before each test. The shared Tooling/Metadata API pools meter calls with a slowly refilling reservoir; after five full syncs in one process the sixth test waited about 8 s on it (measured: that test alone took 0.2 s, the sixth in sequence 8.1 s; with the reservoir topped up, all six tests take 0.2-0.7 s each, default 5 s timeout kept). The same top-up is used by `ingest-auto-retry-e2e.test.ts`.

**Untested**: no real org. Changes made after the pre-scan but before the full run finishes are covered by the next sync only if their SourceMember time is after the new watermark (same as any full sync). Pure-deletion changes of an unsupported type are treated as unsupported (full refresh).

### C-1.8.2-021 (S-1.8.2-003, F03): unsupported SourceMember types are reported, never dropped

**What**: SourceMember rows whose type is not in the map (for example Workflow) used to be skipped silently while the watermark advanced. They are now counted per type and reported as `incremental:unsupportedTypes:Workflow=1`. In explicit incremental mode the watermark is held. In auto they trigger the full refresh (C-1.8.2-020), after which the watermark advances as after any full sync.

**How**: `packages/core/src/extractors/live-org/source-member.ts` (`iterChanges`, new optional `onUnsupported` callback, around lines 36-42 and 72-76); `packages/core/src/ingest/live-ingest.ts` (`unsupportedTypesWarning`, incremental branch around lines 1230-1265, watermark hold at `holdWatermark`).

**Check**: same test file. "a Workflow SourceMember change under auto falls back to full and names the type" and "an unsupported type holds the watermark and warns" (explicit incremental: `lastSyncedAt` unchanged). Without the fix the second one fails (no warning, watermark advanced). `SFGRAPH_AUDIT_REPO=$PWD node docs/audit/2026-11-14-evidence/audit-incremental.mjs` now stops at its first assertion (`mode` is `full`, expected `incremental`), so it no longer prints AUTO_SYNC_DOES_NOT_REFRESH or UNSUPPORTED_CHANGE_MARKS_FRESH.

**Untested**: `iterChanges` still yields nothing for unsupported types (callers that pass no callback see the old behaviour); no other caller exists.

### C-1.8.2-022 (S-1.8.2-003, F03): explicit incremental says plainly what it did not do

**What**: `--mode incremental` keeps its deletions-only behaviour. The warning now says added/modified members were not fetched, that incremental applies deletions only, the watermark is held, and that `--mode full` (or auto) refreshes them. The warning code `incremental:contentNotFetched:count=N` is unchanged.

**How**: `packages/core/src/ingest/live-ingest.ts` incremental branch (message around line 1255). Test: "a modified class is not fetched, is reported, and the watermark is held" (old hash kept, watermark unchanged).

**Check**: same test file; also the README mode paragraph and `docs/CLI.md` `--mode` row describe it.

**Untested**: wording is not asserted beyond the warning code.

### C-1.8.2-023 (S-1.8.2-003, F03): the CLI tells the user

**What**: `sfgraph ingest` prints a plain note after a live sync when auto fell back to full, when incremental left added/modified members unfetched, or when unsupported types were seen (single-org and multi-org paths).

**How**: `reportSyncModeNotes` in `packages/cli/src/commands/ingest.ts`, called next to `reportEmbeddingOutcome`.

**Check**: `pnpm build && pnpm --filter @ryanstark24/sfgraph-cli exec vitest run src/__tests__/ingest-auto-fallback.test.ts` (runs `ingestCmd` twice against a mock org with a real store; the second run, default mode, prints "auto ran a full refresh" with `mode=full` and names `Workflow=1`). Fails with the CLI and core source changes stashed.

**Untested**: the MCP `start_ingest_job` tool only returns the shell command (`sfgraph ingest ...`) and runs no ingest, so it has no result to surface and was not changed or tested for this. Filesystem `--delta` was not touched.
