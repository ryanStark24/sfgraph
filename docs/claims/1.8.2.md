### C-1.8.2-002 (S-1.8.2-001, F01): Typed read facade replaces the Proxy

**What**: `wrapConnectionReadOnly(conn)` no longer returns a Proxy over the raw connection. It returns a frozen plain object (`ReadOnlyOrgConnection`) with only the calls in C-1.8.2-001. The raw connection exists only inside closures. Query objects are awaited into plain result pages, `sobject()` returns `{describe}`, and `metadata.retrieve()` returns `{complete}` (the jsforce locator holds the metadata API and so the connection). There is no pass-through of unknown properties, no bound SDK function, no `_conn`.

**How**: `packages/core/src/extractors/live-org/read-facade.ts` (`createReadFacade`, line 107; interfaces above it); `read-only-proxy.ts:16` (`wrapConnectionReadOnly`, kept as the exported name and still exported from `live-org/index.ts`, which now also exports the facade types and guard); `auth.ts` `ResolvedOrg.conn` is typed `ReadOnlyOrgConnection` and `resolveOrg` wraps at line 116. A method is defined only if the raw object has it at wrap time, so `typeof conn.describeGlobal === "function"` checks in `live-ingest.ts` keep their meaning. Extractor parameters stay `conn: any` because many existing tests pass partial mocks; the typed seam is `ResolvedOrg`, `wrapConnectionReadOnly` and `createReadFacade`.

**Check**: `cd packages/core && npx vitest run src/extractors/live-org/__tests__/read-only-proxy.test.ts -t "read facade"`. Expect 5 passed: exact key set, no write or request surface at any depth, a graph walk (own keys, getters, prototypes, returned handles) that never reaches the raw Connection, its `_transport`, `apex`, `metadata`, `tooling`, `bulk`, `bulk2` or `soap`, plain-data results, and `facade.apex` / `sobject()._conn` / `metadata._conn` being unreachable.

**Untested**: The walk cannot find objects reachable only through running arbitrary SDK code, because the facade holds none. Extractors still take `any`-typed `conn`, so a future extractor could call a method the facade lacks and fail at runtime (it would throw `TypeError`, not write).

### C-1.8.2-003 (S-1.8.2-001, F01): Transport guard on the real jsforce Connection

**What**: `installTransportGuard` (called by `wrapConnectionReadOnly`) wraps two places on the real Connection: `conn.request` and `conn._transport.httpRequest`. jsforce 3.10.15 sends Metadata SOAP through its own `HttpApi` straight to `_transport.httpRequest`, without `conn.request`, so guarding `request` alone would miss it (checked in `jsforce/lib/api/metadata.js`, `soap.js`, `http-api.js`). Allowed: GET and HEAD, and POST to `/services/Soap/m/<version>` whose envelope body is exactly one top-level operation in `SOAP_READ_OPERATIONS` (`listMetadata`, `readMetadata`, `describeMetadata`, `retrieve`, `checkStatus`, `checkRetrieveStatus`), with `_message` (when present) agreeing. The operation is parsed from the envelope, not inferred from the URL. Everything else throws `ReadOnlyViolationError: read-only Salesforce connection: refused <METHOD> <URL> ...` before the transport is called. GET is also refused for `/tooling/executeAnonymous` and `/tooling/runTestsAsynchronous|runTestsSynchronous`, which run Apex (and so can write) over GET.

**How**: `packages/core/src/extractors/live-org/transport-guard.ts`: `SOAP_READ_OPERATIONS` line 31, `STATE_CHANGING_GET` line 44, `soapOperation` line 62 (tokenises the Body, fails closed on anything not exactly one balanced top-level element), `assertReadOnlyRequest` line 97, `installTransportGuard` line 127 (non-writable, non-configurable own properties; idempotent; objects with neither `request` nor `_transport`, such as test doubles, are left alone).

**Check**: `npx vitest run src/extractors/live-org/__tests__/read-only-proxy.test.ts -t "transport guard"`. Expect 7 passed.

**Untested**: Real Salesforce: no org was contacted, so the SOAP envelope shapes come from jsforce's serializer, not from a live org. The OAuth refresh `@salesforce/core` does with its own client does not go through the connection's transport and is not guarded (documented in PRIVACY.md). Streaming (Faye) uses its own transport and is not used by sfgraph. Someone holding the raw connection could still replace `conn._transport`; extractors never hold it.

### C-1.8.2-060 (S-1.8.2-001, F01): API usage reaches the omnistudio quota guard through the facade

**Check**: `cd packages/core && npx vitest run src/extractors/live-org/__tests__/read-only-proxy.test.ts src/extractors/live-org/__tests__/omnistudio-retrieve.test.ts`. ### C-1.8.2-040 (S-1.8.2-009, F11): "Render entire org" enumerates the stored labels

**What**: `/api/full` includes every label stored for the org (OmniScript, DataRaptor, IntegrationProcedure, any other family), not a fixed list. A five-node graph with an OmniScript returns five nodes.

**How**: new store method `SqliteGraphStore.listLabelCounts(orgId)` (packages/core/src/storage/sqlite/graph-store.ts:1601, declared in storage/interfaces.ts:200) reads the label tables and returns each label with its node count for the org. `fullGraph` (packages/web/src/api.ts:264) iterates those labels and asks `listNodesByLabel` for only the remaining room under the limit. The hardcoded `ALL_KNOWN_LABELS` list is gone.

**Check**: `pnpm --filter @ryanstark24/sfgraph-web exec vitest run src/__tests__/web-graph-endpoints.test.ts -t "F11"` (starts the real HTTP server on a temp data dir, GETs `/api/full`). ### C-1.8.2-041 (S-1.8.2-009, F11): exclusions reported apart from the node limit; UI labels from the same source

### C-1.8.2-042 (S-1.8.2-010, F12): capped schema responses have no edges to missing nodes

**What**: In `/api/schema`, an edge is added only when both endpoints are in the returned node set. Neighbours the cap refused are counted in `omittedNodes` and `truncated` is true. With 1 object + 3 consumers and limit 2: 2 nodes, 1 edge, `omittedNodes` 2, no dangling edge.

**How**: `schema()` in packages/web/src/api.ts:316-390: `addNode` returns whether the node is in the set and records refused ids (case-folded) in `omitted`; `addEdge` checks both endpoints. The early `break` when the cap was reached is removed so every seed's neighbours are examined and counted (the node lookup is skipped for refused nodes, so the work stays bounded). Seeds are read by name only (`listQnamesByLabel`, no limit) and go through the same `addNode`, so every refused node, seed or neighbour, is recorded once in one set under its case-folded id. (An earlier version also counted unfetched seeds under synthetic ids, which double-counted; fixed after review.)

**Check**: `... -t "F12"` and `... -t "limit 2"`; `-t "counts an omitted seed once"` (object + 3 fields, limit 2: `omittedNodes` 2) and `-t "counts a refused seed once"` (refused seed also reached by an edge: counted once). Old code returned 3 edges with 2 absent endpoints. Audit runner `audit-repro.mjs` printed `SCHEMA_DANGLING_EDGES` before; after the fix the run stops earlier at the F11 assertion, so that line is not reached (the schema case is covered by the test).

**Untested**: `omittedNodes` counts distinct refused neighbour ids (case-folded) seen while following the wanted relationship types; it does not count nodes that would only appear at a further hop, because the schema view has no further hop.

### C-1.8.2-044 (S-1.8.2-011, F13): search runs in storage and finds names past 25,000

**What**: `/api/search` no longer loads every name. The case-insensitive substring match and the limit run in SQL. `Search49999` in a 50,000-node graph is found.

**How**: new `SqliteGraphStore.searchQnames(orgId, needle, limit)` (graph-store.ts:1614, interface at storage/interfaces.ts:205): per label table `SELECT qualified_name ... WHERE org_id = ? AND qualified_name LIKE ? ESCAPE '\' LIMIT ?`, asking for `limit + 1` rows overall to learn whether more exist. SQLite `LIKE` folds ASCII case, the same fold as the NOCASE column. `%`, `_` and `\` in the user's text are escaped, so they match themselves. `search()` in api.ts:115 calls it; `listAllQnames` and `SEARCH_MAX_SCAN` are gone from the web package.

**Check**: `... -t "F13"`: finds `ApexClass:Search49999` (seeded in 50 batches of 1,000, about 0.5 s), finds it again with a lower-case needle, and the `%`/`_`/`\` cases return only the literal matches. Failed on the old code. Audit runner `audit-scale.mjs` no longer prints `SEARCH_SILENT_CAP`; its assertion `hits.length === 0` now throws (the result is an object, and the hit is found).

**Untested**: a substring `LIKE '%x%'` cannot use an index, so it scans each label table inside SQLite (no JS allocation, stops at the limit). Search time on 50,000 nodes was not benchmarked beyond the test finishing in well under a second; very large orgs were not tried. Non-ASCII case folding follows SQLite NOCASE/LIKE (ASCII only).

### C-1.8.2-045 (S-1.8.2-011, F13): search reports when it stopped

**What**: `/api/search` now returns `{ hits, truncated }` instead of a bare array. `truncated` is true when more matches exist than `limit`.

**How**: `search()` return type in api.ts:115; the one UI consumer, the autocomplete in app.js, reads `.hits`. The previous behaviour (a bare array) is changed on purpose, so `search-bounds.test.ts` now expects `{ hits: [], truncated: false }` for short queries (the buggy-behaviour assertion was only the shape).

**Check**: `... -t "F13"` with `q=Search4&limit=10` returns 10 hits and `truncated: true`.

**Untested**: any other client of `/api/search` outside this repository would see the shape change.
