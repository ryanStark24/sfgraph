### C-1.8.2-010 (S-1.8.2-002, F02): one case-folding key, `nameKey`

- **What**: a single helper, `nameKey`, is the comparison key for names the store holds without case. It folds only ASCII A-Z, which is exactly what SQLite `COLLATE NOCASE` does; non-ASCII letters (`É` vs `é`) stay different, as in the store. It is exported from core (`domain`), so every JavaScript comparison of store names can use it.
- **How**: `packages/core/src/domain/name-key.ts` (`nameKey`, `sameName`), re-exported in `packages/core/src/domain/index.ts`. Used by cross-org comparison, manifest generation and the security audit (claims 011 to 014).
- **Check**: `cd packages/mcp-server && npx vitest run src/tools/__tests__/case-identity.test.ts -t "only ASCII letters fold"`; expect pass. This test also passes on the old code (it guards against over-folding, it is not a regression test for the bug).
- **Untested**: other places in the repo that compare names in JavaScript (not found by me, not searched exhaustively) still use exact or `toLowerCase` comparison.

### C-1.8.2-011 (S-1.8.2-002, F02): cross-org diff matches names without case

- **What**: `ApexClass:BillingService` in the source org and `ApexClass:billingservice` in the target are one component. Same hash: not in `onlyInA`, `onlyInB` or `changed`. Different hash: one entry in `changed`, shown with the source org's spelling. A one-sided entry keeps its own spelling.
- **How**: `packages/core/src/analyze/cross-org.ts` lines 120 to 131: the two Maps are keyed by `nameKey(qualifiedName)` (values keep the original `NodeFact`); the comparison loop is unchanged. `hideOneSided` is unchanged.
- **Check**: `cd packages/mcp-server && npx vitest run src/tools/__tests__/case-identity.test.ts -t "same hash"` (five cases: class, field `CustomField:Account.Foo__c` vs `account.foo__c`, method `ApexMethod:BillingService.Run(0)` vs `billingservice.run(0)`, namespaced object `ns__Obj__c` vs `NS__obj__C`, namespaced field) and `-t "different hash"`. They call the `cross_org_diff` and `deployment_manifest_gen` tool handlers over two real SQLite stores. Expect 16 of the 17 tests in that file to fail with the core source files from before this change restored (I ran it that way) and all 17 to pass with it.
- **Untested**: `point_in_time_diff` and snapshot diffs compare BINARY by design (documented in `snapshot-versions.ts`) and were not changed. Duplicate keys inside one store cannot occur (the store's unique key is NOCASE), so which of two same-key rows wins was not tested.

### C-1.8.2-012 (S-1.8.2-002, F02): a component is never both deployed and deleted

- **What**: `generateManifest` has a final invariant. After building both member sets, any destructive member with the same metadata type and the same member name (by `nameKey`) as a package.xml member is dropped from destructiveChanges.xml and listed in the new `droppedFromDestructive` field (`[{ type, member }]`), and in the tool text ("left out of the delete file because the package file deploys the same component"). `summary.byType` and `summary.removed` are reduced by the dropped entries.
- **How**: `packages/core/src/analyze/deployment-manifest/generate.ts` lines 180 to 195 (invariant), 43 (type), 204 and 212 (summary and result); text in `packages/mcp-server/src/tools/deployment_manifest_gen.ts`. After claim 011 the case-only route into this branch is closed, so the branch is a backstop. It does fire for a real case I found: two sharing rules of one object map to the same `SharingRules` member (`Account`); a rule changed in the source and another rule only in the target would have produced `Account` in both files.
- **Check**: `npx vitest run src/tools/__tests__/case-identity.test.ts -t "final invariant"` and `-t "real removal next to"`.
- **Untested**: the invariant keys on type and member name, so it cannot see two different types that overlap in meaning (for example a `CustomObject` and its fields).

### C-1.8.2-013 (S-1.8.2-008, F10): the field access matrix and FLS gaps use the canonical key

- **What**: a grant edge to `CustomField:account.secret__c` and a field node `CustomField:Account.Secret__c` give one matrix entry (display name: the field node's own spelling) and no FLS gap. Grants that differ only in case merge into one entry with all grantors. A granted field with no node is shown with the first grant's spelling. The object filter (`Account`, `account`, `CustomObject:ACCOUNT`) and the field filter (any case) match without case. System-field exclusion (`CreatedById` etc.) also ignores case.
- **How**: `packages/core/src/analyze/security.ts`: `matchesFilter` (lines 154 to 168), the matrix keyed by `nameKey` with a spelling map (lines 184 to 205), the gap test (line 235), display via `store.getNode` (after line 240), `SYSTEM_FIELD_KEYS` (122, 140). The single-field path in `packages/mcp-server/src/tools/security_audit.ts` (`fieldSecurityAudit`) returns the node's spelling.
- **Check**: `npx vitest run src/tools/__tests__/case-identity.test.ts -t "security_audit and export_sarif"` (tests "a grant to account.secret__c", "an object filter in any case", "a field filter in any case", "two grants that differ only in case", "a granted field with no node", "system fields are excluded").
- **Untested**: a store holding the same grant spelled two ways AND two field nodes differing only in case (cannot exist under NOCASE).

### C-1.8.2-014 (S-1.8.2-007, F09): sharing rules are described as record sharing, in a new bucket

- **What**: the bucket is now `sharingEditAccess` (plus `sharingEditAccessTotal`), with `sharingRuleAccess: [{ qualifiedName, access: "Edit" | "All", audience? }]`, so Edit and All are kept apart and the audience is read from what the parser stores for an ingested project: the `SHARING_TO_GROUP` and `SHARING_TO_ROLE` edges (`group: X`, `role: X`, `role and subordinates: X`) and `kind: "guest"` on the node (`guest users`; the guest's site name is not stored), joined with "; ". Nodes with no such edges fall back to a `sharedTo`, `shareTo` or `audience` attribute (a string, or an object printed as `key: value`). No parser or hash change. Absent when none exists. `sharingFullAccess` and `sharingFullAccessTotal` remain in the `security_audit` output as deprecated aliases with the same content (documented in `docs/TOOLS.md` and in the type). The SARIF rule is renamed `security.sharing-full-access` to `security.sharing-edit-access`, level `note` (was `warning`), and its text says: record-level access from a sharing rule and its audience; record sharing only; not object (CRUD) or field permissions; not Modify All or View All (permission set and profile settings); the analysis does not read org-wide defaults or work out any user's effective access. Messages read "<rule>: sharing rule gives Edit access to records to <audience> (record sharing only; says nothing about object or field permissions)". `security_audit` text and summary use the same wording. The cached finding message for `sharing.full_access` in `populateSecurityFindings` is reworded; its rule id is unchanged.
- **How**: `packages/core/src/analyze/security.ts` (`SharingRuleAccess`, `audienceFromEdges`, `sharingEditRules`, shared by `securityAudit` and the single-field tool path), `packages/core/src/analyze/findings.ts` (rule at line 124, adapter near line 183), `packages/core/src/analyze/populate.ts`, `packages/mcp-server/src/tools/security_audit.ts`. Consumers found: only the tests, `docs/TOOLS.md` and the t4 golden; no skill or other package reads `sharingFullAccess`.
- **Check**: `npx vitest run src/tools/__tests__/case-identity.test.ts -t "sharing: Edit and All"` and `-t "SARIF rule text"` (attribute fallback only); `npx vitest run src/tools/__tests__/sharing-audience-ingest.test.ts` (a real `*.sharingRules-meta.xml` with a criteria rule to a group, an owner rule to a role and subordinates, and a guest rule goes through `liveIngest`, then `security_audit` and `export_sarif`; both tests fail with the old `security.ts` copied back in, and pass with the fix); `npx vitest run src/tools/__tests__/audit-perf-06.test.ts -t "caps sharingEditAccess"`; `npx vitest run src/tools/__tests__/t4-reports` (golden `expected/t4-reports.json` updated for `security_audit.*`, `export_sarif.all` and `deployment_manifest_gen.ab`: new fields and new wording; the t4 test "security_audit describes sharing as record access" replaces the one that asserted "(edit or full access)").
- **Untested / judgement**: the guest rule's site name (`guestUser`) is not persisted by the parser, so a guest audience reads only "guest users". Rules shared to other recipient kinds (for example `allInternalUsers`, `territory`) have no edge and show no audience. Renaming the SARIF rule id breaks anyone who suppressed the old id; I judged the old id itself misleading. The org-wide default is not read, so nothing here says anything about OWD.
