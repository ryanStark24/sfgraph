### C-1.8.2-030 (S-1.8.2-004, F04): dead-code scans read every node and apply the filters in the query

**What**: `dead_code_audit` and the dead-code score cache no longer stop at the first 10,000 nodes per label. With 10,001 unreferenced classes, `pattern="Scale10000"` finds the class after the old cut-off, with and without the cache.

**How**: `scanDeadCode` (packages/core/src/analyze/dead-code.ts:323) walks each scored label with `scanLabel` (packages/core/src/analyze/scan.ts:64): keyset pages of 500 rows by rowid through the new `SqliteGraphStore.listNodesPage` (packages/core/src/storage/sqlite/graph-store.ts:1381), so memory is bounded by the page size. `label` and `pattern` become a SQL LIKE pre-filter (`nameLikePattern`, scan.ts:50, `_` escaped) applied before the page limit; the tool's exact glob matcher (moved to core as `makeScanFilter`) still runs on what comes back. `populateDeadCodeScores` (populate.ts) uses the same scan. `readCachedDeadCode` / `collectDeadCode` (packages/mcp-server/src/tools/dead_code_audit.ts, _analysis-cache.ts) read the stored coverage and fall back to a live filtered scan when a cache's scan was incomplete and a filter is given. The unscored-label path (`liveZeroInbound`) pages too (its 20,000 cut-off is gone). `DEAD_CODE_ALGORITHM_VERSION` is 6, so caches written before are recomputed.

**Check**: `cd packages/mcp-server && npx vitest run src/tools/__tests__/complete-scans.test.ts -t "dead_code_audit above"` (3 tests: pattern on the 10,001st class without cache; total and coverage without a filter; with the cache populated, plus SARIF live and cached). `cd packages/core && npx vitest run src/analyze/__tests__/complete-scans-core.test.ts -t "keyset"`. Expected: pass. With the source changes stashed, all 22 tests of complete-scans.test.ts fail.

**Untested**: no real-org-sized graph; 10,001 nodes is the largest tested. Name patterns with non-ASCII letters: the SQL LIKE pre-filter is ASCII case-insensitive only, so a pattern differing from a name only in the case of a non-ASCII letter would be missed (Salesforce API names are ASCII).

### C-1.8.2-031 (S-1.8.2-004, F04): the governor scan reads every method and trigger

**What**: `findGovernorRisks` no longer stops at the first 20,000 nodes per label: an in-loop SOQL on method 20,001 is reported, live and with the cache populated, in `governor_risk_check` and `export_sarif`. The cache population paths (governor risks, test coverage, sharing findings) lost their fixed 10,000 / 50,000 limits too.

**How**: `scanGovernorRisks` (packages/core/src/analyze/governor.ts:84) pages through `ApexMethod`, `TestMethod` and `ApexTrigger` with `scanLabel`; `findGovernorRisks` returns its risks. `populateGovernorRisks`, `populateTestCoverage` and `populateSecurityFindings` (populate.ts) page the same way. `collectGovernorRisks` (packages/mcp-server/src/tools/_analysis-cache.ts) returns the scan's coverage.

**Check**: `npx vitest run src/tools/__tests__/complete-scans.test.ts -t "governor scans above"` (20,001 methods, risk on the last one; no cache, then cache populated and SARIF). Expected: 2 tests pass.

**Untested**: scan time grows with the added per-method snippet read (the audit's 20,001-method seed: about 380 ms live, was about 80 ms).

### C-1.8.2-032 (S-1.8.2-004, F04): scanned, total and complete carried through caches, MCP text and SARIF

**What**: every scan reports how much it examined. "No findings" is said only for a complete scan; otherwise "none in the N of M inspected". The only remaining hard cap is a safety limit (`scanLimits.maxNodesPerLabel`, 5,000,000 per label) that marks the scan incomplete.

**How**: `ScanCoverage` and `scanLimits` (packages/core/src/analyze/scan.ts). Caches record coverage in the new `_sfgraph_analysis_coverage` table (`writeScanCoverage` / `readScanCoverage`, populate.ts:34, :49; created on demand, no migration). MCP: `data.scan` on `dead_code_audit` and `governor_risk_check` (`{scanned,total,complete}`), `data.scanCoverage` on `export_sarif`; the in-short, summary and details texts change when `complete` is false. SARIF: `emitSarif` writes `runs[0].properties.sfgraphScanCoverage` and `sfgraphScanComplete`, and a warning `toolExecutionNotifications` entry per incomplete scan (packages/core/src/render/sarif.ts:181). With a filter, `total` counts the nodes in scope (labels and pattern), not the whole graph.

**Check**: `npx vitest run src/tools/__tests__/complete-scans.test.ts -t "safety limit"` (limit lowered to 100 on 150 to 151 nodes: dead_code_audit and governor_risk_check say "in the 100 of ... inspected" and never "No spots found where..."; SARIF properties and notification; a partial cache is reported incomplete and a filtered question rescans live). Expected: 4 tests pass. The existing golden `expected/t4-reports.json` was updated by hand-regeneration for the ten affected cases (data gains `scan`, Technical details text changes); `_t4-reports.ts` assertions were reworded for the new "no captured incoming references" text.

**Untested**: the safety limit is exercised only by lowering it in tests; the 5,000,000 default was never reached. A store without `listNodesPage` (only the SQLite store exists) uses a one-read fallback that was not run in a test.

### C-1.8.2-033 (S-1.8.2-005, F06): "no captured incoming references", with external entry points kept apart

**What**: the tool title, summary, in-short text, follow-up and SARIF messages say "no captured incoming references" and that callers outside the graph (integrations, the UI, schedules) are not captured. The follow-up no longer says `trace_upstream` can confirm nothing uses a piece; it says what the graph does have and that external callers must be checked. Known external entry points are listed in their own section and in `data.externalEntryPoints` (with `kinds`), and never get more than low confidence; the age score and the `stale_freshness` reason stay as a separate signal.

**How**: `externalEntryPoints` (packages/core/src/analyze/entry-points.ts:77) reads parser facts: member methods' `httpVerbs` (an `@Http*` method means a `@RestResource` class; the class annotation is not stored), `isInvocable`, `auraEnabled`, `isRemote`, `webservice` / `global` modifiers on the class and methods, and IMPLEMENTS edges to Schedulable, Database.Batchable, Queueable, Messaging.InboundEmailHandler. `scoreDeadCode` (dead-code.ts:464) adds the reasons `external_entry_point` and `entry_point:<kind>` and caps confidence at "low". The reasons are stored in the score cache, so the cached and live paths agree. SARIF: rule text and each result message carry the caveat; results have `externalEntryPoint` and `entryPointKinds` properties (findings.ts). Skill `packages/skills/skills/sf-dead-code-audit/SKILL.md` and `docs/TOOLS.md` updated.

**Check**: `npx vitest run src/tools/__tests__/complete-scans.test.ts -t "F06"` (filesystem ingest of a `@RestResource` class, a `Schedulable` class, a plain old class; files dated 2019; run without and with the cache: the endpoint and the job are in `externalEntryPoints` with confidence `low` and `stale_freshness`, the plain class is `high`; text has no "nothing uses"; SARIF marks them). Expected: 6 tests pass. `audit-repro.mjs` still prints `REST_ENDPOINT_DEAD ... "kind":"dead"` because the node is still a zero-inbound candidate (by design); it is now also marked as an entry point (`candidate.externalEntryPoints`), which the runner does not print.

**Untested**: platform-event triggers are not handled because triggers are never dead-code candidates (not in `DEAD_CODE_LABELS`; the platform fires them). `webservice` is read from method modifiers, which the regex parser keeps only for some declarations: a one-line `webservice static void w(){}` after another one-line method lost its modifiers in a probe (a pre-existing parser quirk, not changed). Flow, LWC and other labels have no entry-point detection.

### C-1.8.2-034 (S-1.8.2-006, F07): `unbounded_query` and `no_bulk` work on normally parsed Apex; one shared detector

**What**: both checks fire on filesystem-ingested Apex, live and cached. `return [SELECT Id FROM Account];` is unbounded; a query with `LIMIT`, any `WHERE` (including `WHERE Id = :id`), `COUNT()`, or a `__mdt` source is not. `no_bulk`: a trigger that reads `Trigger.new[0]` / `Trigger.old[0]` (or `.get(0)`), has no `for` loop over `Trigger.new/old/newMap/oldMap` and uses those collections nowhere else (passing them to a handler counts as handling the collection).

**How**: packages/core/src/analyze/governor-source.ts (`detectUnboundedQueries`:76, `detectNotBulkTrigger`:115, definitions in the file header) reads the stored snippet of each method or trigger (`unitSourceRisks`:149); a unit with no snippet is not checked (the EXECUTES_SOQL edge text is not used: one edge covers every query on the same object and the text is cut at 500 characters). `scanGovernorRisks` (live) and `populateGovernorRisks` (cache) both call it; the old inline detector in populate.ts now calls it for the legacy `source`/`body` attribute path. The old `no_bulk` rule (any trigger without the text `Trigger.new`) is replaced because it flagged every trigger that delegates to a handler; the test asserting it (`governor-risks-detection.test.ts`, "flags trigger without Trigger.new") was changed to the new definition and a negative test added. Rule text in `RULE_CATALOG`, the tool details and `sf-governor-risk-fix` skill state the definitions.

**Check**: `npx vitest run src/tools/__tests__/complete-scans.test.ts -t "F07"` (filesystem ingest of `Queries.cls` with an unbounded, a LIMIT, a WHERE Id and a COUNT query, and three triggers; `governor_risk_check` without and with the cache, `export_sarif`, and the `_sfgraph_governor_risks` rows). Expected: 7 tests pass: one `unbounded_query` (`ApexMethod:Queries.everything(0)`), one `no_bulk` (`ApexTrigger:OneAtATime`). Core: `npx vitest run src/analyze/__tests__/complete-scans-core.test.ts` (calibration table). `audit-repro.mjs` still prints `UNBOUNDED_QUERY_UNREPORTED` with empty lists: that runner merges parse nodes and edges but never stores the snippets (`result.snippets`) that real ingest stores, so the detector has nothing to read there; the filesystem-ingest tests above are the proof.

**Untested**: no real-org calibration of noise: any `WHERE` is treated as bounded and selectivity is not judged; a query inside a string-built dynamic SOQL is not looked at; class-level code outside methods (field initialisers) has no snippet and is not scanned. Detection quality depends on the regex parser's snippets (a method it fails to find has no snippet).
