### C-1.8.1-030: workflow field updates are per-update writers (S-1.8.1-009)

- **Done:** each `<fieldUpdates>` block becomes a `WorkflowFieldUpdate:<Object>.<Name>` node (contained by `Workflow:<Object>`) with a `WRITES_FIELD` edge to its target field. `analyze_field` already follows `WRITES_FIELD`, so no tool change was needed.
- **How:** `packages/core/src/parsers/rules/workflow.yml` (node at line 38, edges from line 70). Existing `WORKFLOW_UPDATES_FIELD` edges are unchanged.
- **Check:** `packages/core/src/parsers/rules/__tests__/workflow-field-lineage.test.ts`, test "emits WorkflowFieldUpdate nodes with WRITES_FIELD and READS_FIELD edges"; run `cd packages/core && npx vitest run src/parsers/rules/__tests__/workflow-field-lineage.test.ts` (expect 1 passed).

### C-1.8.1-031: workflow rule and update formulas and criteria read fields (S-1.8.1-009)

- **Done:** `READS_FIELD` from a rule to the fields in its `<criteriaItems><field>` (`Obj.Field` taken as-is, a bare name prefixed with the workflow's object) and in its `<formula>`; `READS_FIELD` from a field update to the fields in its `<formula>`. Formula matching is the approval-process pattern (bare `X__c` names; `Rel__r.F` reads `Rel__c`; names in string literals and after a `.` or `$` are skipped). A rule gets `WORKFLOW_TRIGGERS` to each `<actions>` entry of type `FieldUpdate`.
- **How:** two new selector functions `flatChildren` and `flatMatches` in `_selectors.ts` (lines 194-226) pair each match with its owning rule or update; used by `workflow.yml`.
- **Check:** same test as above (asserts the exact edge sets of both updates and both rules, and that the field's incoming `WRITES_FIELD` names the update). Standard (non-`__c`) fields referenced in formulas are not matched, same as the approval-process rule. Golden fixture `packages/core/src/parsers/__tests__/fixtures/long-tail/workflow.expected.json` was regenerated (adds the new node and edges); test "long-tail parsers golden > Workflow" passes.

### C-1.8.1-032: SObject.put through a same-class helper is a write (S-1.8.1-010)

- **Done:** a helper whose parameter flows into `<param>.put(<String param>, …)` produces a `WRITES_FIELD` edge (`via: sobject-put-helper`) from the calling method for each call site passing a string literal field, on the sObject type of the record argument when it is a typed variable, parameter, field or `new T()`. Unqualified, `this.` and `<OwnClass>.` calls count.
- **How:** `collectPutHelpers` and the call-site scan in `packages/core/src/parsers/apex/name-refs.ts` (helper collector line 388; call-site loop before the "Field tokens" block); wired in `class.ts` (`putHelpers`, passed to `emitNameRefEdges` for method bodies).
- **Check:** `packages/core/src/parsers/apex/__tests__/put-helper.test.ts` (4 tests: typed param and own-class-qualified call; typed local; variable field name / untyped `SObject` / unknown variable give no edge; ambiguous overloads give no edge). Run `cd packages/core && npx vitest run src/parsers/apex/__tests__/put-helper.test.ts`.
- **Limits:** same class only (cross-class static calls are not resolved here, so a helper in another class is not followed); one hop (a helper forwarding to another helper is not); helpers of the same name and arity declared twice are dropped; a parameter reassigned inside the helper before `put` is not detected. Call sites outside method bodies (field initialisers) are untested.
