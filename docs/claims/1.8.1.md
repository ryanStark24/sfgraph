### C-1.8.1-002 Suffix fallback for unknown folders (S-1.8.1-001)

- Done: any other `<folder>/**/*.<type>-meta.xml` under a metadata root becomes an opaque member typed from its suffix (`gadget` becomes `Gadget`; `SUFFIX_TYPE_OVERRIDES` fixes irregular names such as `app` to `CustomApplication`, `resource` to `StaticResource`, `translation` to `Translations`).

Coverage needs no change: the opaque nodes show in `unknownTypes` when they have no rule and no generic edges.
- Overlap guard: the fallback skips any folder that is or contains another discovered metadata root (so `force-app/main` is not walked as an unknown folder when `force-app/classes` and `force-app/main/default` are both roots), and `walkPackage` drops any member whose source path was already yielded. - Judgement: the type map is a hand-written override list, not an existing registry (sfgraph has none for suffixes). An unlisted suffix is only capitalised, so a type whose name differs from its suffix and is missing from the list gets a wrong-cased type name (untested for types outside the list).

### C-1.8.1-020 (S-1.8.1-003): project ingest takes `lastModifiedAt` from git

- Done: `FilesystemMetadataSource.iterIndexed` builds a `ChangeTimes` lookup once per run (`packages/core/src/extractors/filesystem/change-times.ts`, class `ChangeTimes`, `load`) and every member's `ref.lastModifiedAt` comes from it (`extractors/filesystem/index.ts`, `makeRef`, `times.lookup`; DataPacks in the `iterIndexed` load wrapper).
- How: the lookup runs a fixed handful of git calls through an injectable runner (`rev-parse`, one `log --name-only -z`, one `diff HEAD`, one `ls-files --others`), never one process per file; each has a 60 s timeout and a 128 MB output cap, and on either the partial output is used. A clean tracked file gets its last commit time (`%ct`); a file edited since HEAD or untracked gets its mtime (newest); not a git tree, git failing, or a file git does not know gets mtime. A bundle or object folder (the whole object folder: fields, record types, rules) takes its newest file. The git safety config is the one `wip-changed-files.ts` uses (`safeGitConfig`, now exported).
- Check: `pnpm --filter @ryanstark24/sfgraph-core exec vitest run src/extractors/filesystem/__tests__/change-times.test.ts` (5 tests). "buckets match back-dated commits" makes commits 2, 45 and 400 days old with GIT_AUTHOR_DATE/GIT_COMMITTER_DATE, sets every mtime to now, and expects hot, current, dead. "a file edited since HEAD..." expects an edited and an untracked file hot. "a bundle or object folder..." expects the object at 2 days (newest field). "outside git..." expects mtime (hot, and a 200-day-old file stale). "history is read in a few batched calls..." counts runner calls for 40 classes: at most 5, exactly one `log`.
- Untested: a repo large enough to hit the 60 s timeout (partial-output path); submodules; shallow clones (a file last changed before the shallow boundary reads as the boundary commit time).

### C-1.8.1-021 (S-1.8.1-003): the change time reaches the nodes, for project, org and delta ingest

- Done: `parseMember` (`packages/core/src/ingest/parse-member.ts`, `stampSourceChangeTime`) replaces the parse-time `lastModifiedAt` on every node a member produces with `ref.lastModifiedAt` when it is a valid date; parse time stays the fallback when the source gave none. Parse-pool workers, the serial path and delta's pre-parse all go through `parseMember`, so delta ingest follows the same rule.
- Org ingest: the extractors already set `ref.lastModifiedAt` from `LastModifiedDate` (Apex, LWC, Flow, OmniStudio, Vlocity, security, integration, generic metadata and sobject), so they now take effect. Members the extractor has no date for (custom settings, describe-built objects in `object.ts`, OmniStudio retrieve) still use ingest time.
- Check: the "buckets match" test above runs the full `liveIngest`; `freshness_report` reads the same `lastModifiedAt` through `analyze.freshnessScore`. Docs: `docs/TOOLS.md` under `freshness_report`.

### C-1.8.1-023 (S-1.8.1-003): an existing graph heals on upgrade

- Problem: `mergeNodes` only rewrote a node row when its `sourceHash` changed (`hash-salts.ts` says so), so a 1.8.0 graph re-ingested by 1.8.1 without `--rebuild` would have kept every ingest-time `lastModifiedAt` for unchanged members. (A `--delta` after the version bump already does a full rebuild, since the member-row generation includes the core version.)
- Fix (supersedes the earlier `MIN()` rule, which kept a stale old stamp when the source time legitimately advanced without the node hash changing, e.g. a field file added under an object folder): `NodeFact` has an optional merge-time flag `lastModifiedAuthoritative` (`domain/node-fact.ts`), set by `stampSourceChangeTime` (`ingest/parse-member.ts`) whenever the stamp came from the source (commit time, file mtime, org LastModifiedDate). In `mergeNodes` (`storage/sqlite/graph-store.ts`, `updateUnchangedAuthStmt`) an unchanged-hash node takes an authoritative stamp (heal or advance) and keeps its stored value against an ingest-time fallback. The flag is never stored.
- No churn: the unchanged branch writes two columns of the node row and nothing else; no triggers exist on node tables, and edges, FTS, snippets and embeddings are keyed off the hash and are not touched.
- Check: `change-times.test.ts` test "an existing graph with ingest-time stamps heals on a non-rebuild re-ingest of unchanged files": ingest back-dated commits, overwrite every ApexClass `last_modified_at` with now (the 1.8.0 shape), re-ingest the same files with `rebuild: false`, expect dead/hot by git; a third run keeps the 400-day age.
- Also: "a change the node hash does not see (a field file) advances the object's time on re-ingest" (object committed 400 days ago, field committed 2 days ago, non-rebuild re-ingest reads 2 days) and "mergeNodes: an ingest-time fallback never overwrites an unchanged node; an authoritative stamp does" (fallback later/earlier ignored; authoritative advance and heal applied).
- Untested: the same heal for a live-org graph (same `mergeNodes` path, no live org).

### C-1.8.1-024 (S-1.8.1-003): DataPacks and folder members use their newest file, in git and outside it

- DataPacks: `FilesystemMetadataSource.iterIndexed` load wrapper (`extractors/filesystem/index.ts`) now looks up the pack FOLDER (`path.dirname` of the `_DataPack.json` key), matching what `indexDataPacks` fingerprints and `loadPack` inlines, instead of only the main file.
- Outside git: `ChangeTimes.lookup` (`change-times.ts`) for a path git has no answer for now uses `newestMtime`, the newest descendant file mtime (bounded walk, 5000 entries, skips `.git` and `node_modules`, memoized), instead of the directory's own mtime, which an in-place file edit does not bump.
- Check: `change-times.test.ts` tests "outside git, a folder member takes its newest file, not the folder mtime" (object at 3 days with a 300-day folder and object file) and "a DataPack takes the newest file of its folder, not just _DataPack.json" (1 day with a 300-day main file).
- Ignored files: a directory's time is the max of git's time for its tracked files and the mtime of descendant files git has no time for (`ChangeTimes.newestUntracked`, same bounded memoised walk, `node_modules` and `.git` skipped, tracked files not re-statted). Test "a folder member counts ignored descendant files git does not list".
- Untested: a folder with more than 5000 entries (the walk stops and uses what it saw).

### C-1.8.1-025 (S-1.8.1-003): merge-conflict resolutions, and one known limitation

- Merges: the single `git log` in `ChangeTimes.fill` (`change-times.ts`) now passes `-c` (combined diff), so a file changed while resolving a conflict is attributed to the merge commit, not an older parent. `parseGitLog` needed no change. Test: "a file changed while resolving a merge conflict takes the merge commit's time" (real conflicting merge in a temp repo, back-dated 500/400/300/5 days; resolved file reads 5 days, an untouched file keeps 500).
- Not handled (known limitation, untested): a tracked child file deleted locally without a commit leaves its folder (object, bundle, DataPack) at the old git time: the folder's time is the max over files that still exist, and the deletion is not a change time we can read. The next commit or full rebuild after the commit heals it.
- Not handled (known limitation, untested): content changed and then reverted before the next delta. The node hash is then unchanged, so `applyDelta` (`ingest/delta.ts`, the unchanged-member skip) never applies the new commit time; the next full ingest heals it. Rare, so left alone.

### C-1.8.1-042: shallow clones give no authoritative change time for boundary files (S-1.8.1-014)

- **What:** in a shallow repository, a file whose newest visible commit is a shallow boundary commit has an unknown real change time. Its lookup is `null`, so no authoritative stamp is written: the ingest-time fallback applies, and a stored stamp is kept (the existing `lastModifiedAuthoritative` flag, `graph-store.ts` merge, is not set). Files changed after the boundary keep their commit time; untracked or edited files keep their mtime.
- **How:** `packages/core/src/extractors/filesystem/change-times.ts`: `shallowBoundary` (line 264; one `rev-parse --is-shallow-repository --git-path shallow` call, then reads the shallow file), the log format now carries `%H` (`parseGitLogDetailed`, line 126), boundary hashes go to the `unknown` set (fill, around line 218), `lookup` returns null for them (line 291). Fixed number of git calls (rev-parse x2, one log, diff, ls-files others), never per file.
- **Check:** `pnpm --filter @ryanstark24/sfgraph-core exec vitest run src/extractors/filesystem/__tests__/change-times.test.ts -t "shallow"` (2 tests): "a shallow clone gives no authoritative time to files last seen at the boundary" makes three back-dated commits (400, 45, 2 days) in a temp repo, `git clone --depth 2 file://...`, and expects the 2-day file to have its commit time, the boundary (45-day) and older files `null` (not the clone's "now" mtime), at most 6 git calls and exactly one `log`; "a shallow clone still uses mtime for untracked files". Untested: the end-to-end ingest keeping a previously stored stamp from a shallow re-ingest (it relies on the `mergeNodes` rule, covered by "mergeNodes: an ingest-time fallback never overwrites an unchanged node"); and a shallow repository with `git worktree` or a custom `GIT_DIR`.

### C-1.8.1-043: a git log timeout or truncation gives no authoritative time to unreached files (S-1.8.1-014)

- **What:** when the `git log` call times out, hits the byte cap or fails, tracked files the partial output did not mention get no authoritative stamp (not their mtime). Files git does not track at all (untracked, ignored) still use their mtime.
- **How:** `change-times.ts`: `GitRunner` may now return `{ stdout, partial: true }` (`execGit` does so on timeout/overflow with some output) or `null`; `fill` (line 218 `partial`, line 225 one extra `git ls-files -z` to list tracked files) adds tracked files not seen in the log to `unknown`.
- **Check:** `pnpm --filter @ryanstark24/sfgraph-core exec vitest run src/extractors/filesystem/__tests__/change-times.test.ts -t "timeout"`: an injected runner returns `null` for `log` (timeout with no output): both tracked classes are `null`, the untracked one has its mtime; a runner truncating the log after the newest commit: the newest commit's file has its time, the older tracked file is `null`, the untracked file keeps its mtime. Untested: a real 60 s timeout or 128 MB overflow (simulated by the runner only).
