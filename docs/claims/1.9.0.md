## Async work in a loop (S-1.9.0-001, D02)

### C-1.9.0-001: `governor.async-in-loop`

**What**: `governor_risk_check` reports `risk: "async_in_loop"` for `System.enqueueJob`, `Database.executeBatch`, `EventBus.publish`, `Messaging.sendEmail`, and a call to an `@future` method inside a `for`, `while` or `do` loop body of a method or trigger. Fields added to the risk (all optional): `ruleId` (`governor.async-in-loop`), `severity` (`high`), `file` (the node's `sourceUri`), `line` (file line), `message`. `evidence` is the source line.

**How**: detector `packages/core/src/analyze/apex-code-checks.ts` `detectAsyncInLoop` (line 68), reusing `computeLoopRanges` (the loop logic of the existing in-loop checks) on the comment- and string-masked body. `@future` methods come from the `isFuture` attribute (`futureMethodKeys`, `analyze/governor.ts` line 79); a call matches as `Class.method(` or, inside the same class, `method(`. Wired in `scanGovernorRisks` (`analyze/governor.ts` line 203). Text comes from the method's stored snippet, so it works on graphs ingested before 1.9.0.

**Check**: `cd packages/core && npx vitest run src/analyze/__tests__/code-checks.test.ts -t "async"` (detector cases and the ingest case "governor: async work in a loop"); `cd packages/mcp-server && npx vitest run src/tools/__tests__/code-checks-tools.test.ts`. Expect pass. Fixture `packages/core/src/analyze/__tests__/fixtures/code-checks-project/.../classes/VisitTriggerHandler.cls` (positives at lines 6, 14, 15, 19, 27, 39; negatives `bulkified`, `notAsync`), `triggers/VisitTrigger.trigger` line 3. Expected 7 risks, none for the negatives.

**Untested / limits**: direct only (a loop calling a helper that enqueues is not followed); an `@future` method called through an instance variable (`svc.notify(...)`) is not matched; class-level initialisers are not scanned (only methods and triggers); `Database.executeBatch`/`enqueueJob` inside a lambda or inner-class method are judged per method. Severity is fixed at high; limits per call are not counted (one call in a loop is reported even if the loop is bounded to one iteration).

## SOQL / SOSL injection (S-1.9.0-002, D08)

### C-1.9.0-002: `security.soql-injection`

**What**: `security_audit` returns `data.codeFindings[]` (additive) with `ruleId: "security.soql-injection"`, `severity: "high"`, `qualifiedName`, `file`, `line` (the call's line), `message`, `evidence`, `variable` (the tainted parameter) for `Database.query`, `queryWithBinds`, `countQuery`, `countQueryWithBinds`, `getQueryLocator`, `getQueryLocatorWithBinds` and `Search.query` whose string is built by concatenating a method parameter, or a variable assigned from one, that did not pass through `String.escapeSingleQuotes`. Not reported: literals and numbers, escaped values (inline, by an escaped variable, or by reassigning the parameter), `:bind` text inside the literal, `valueOf` conversions, Integer/Long/Decimal/Double/Boolean/Id/Date/Datetime typed values and lists or sets of them, `Schema`/describe-derived names, ALL_CAPS constants and `Class.CONSTANT`.

**How**: `packages/core/src/parsers/apex/soql-injection.ts` (`InjectionAnalyzer` line 138, `detectSoqlInjection` line 340) runs at parse time because a method's stored body has no parameter list; `soqlInjectionAttr` (`parsers/apex/class.ts` line 461, called line 1346; trigger: `parsers/apex/trigger.ts` line 77) stamps `soqlInjection` on the method/trigger node. `analyze/code-security.ts` `scanCodeSecurity` (line 55) reads it (test code skipped). `security_audit.ts` calls it (line 113), only when neither `object` nor `field` narrows the audit. Apex node hash salt is now `apex-attrs:v14` (`parsers/hash-salts.ts`); trigger nodes now hash with the salt too.

**Check**: `cd packages/core && npx vitest run src/analyze/__tests__/code-checks.test.ts -t "detectSoqlInjection|SOQL injection"`. Expect pass: positives `search` (line 13, `term`), `countByOwner` (19), `byRegion` (27, `region`), `find` (33, Search.query); eleven negatives silent (escaped inline, escaped variable, reassigned+escaped parameter, bind, constants, Schema names, typed params, valueOf, comment, string mention, unknown field).

**Untested / limits**: per-method, flow-insensitive. Class fields, values returned by another method, for-each variables and instance calls are not traced and are therefore not reported (low false positives over completeness); `String.format` arguments are matched by variable name only; a conditionally escaped parameter (`if (x) term = escape(term)`) is treated as escaped. A graph ingested before 1.9.0 has no `soqlInjection` attribute; re-ingest. The 9 negatives and 4 positives are synthetic; no real project was scanned apart from the blind project (C-1.9.0-006).

## LWC / Aura DOM injection (S-1.9.0-003, D13)

### C-1.9.0-003: `security.dom-injection`

**What**: `security_audit` `data.codeFindings[]` also carries `ruleId: "security.dom-injection"` for an assignment to `innerHTML` or `outerHTML` (including `+=`), or an `insertAdjacentHTML(...)` call, in LWC and Aura component JS. Severity `high`, or `low` when the value is a plain string literal. In an LWC whose template declares `lwc:dom="manual"` the message says so. Not reported: reading, comparing, `textContent`, clearing with `''`/`""`, and comments.

**How**: `packages/core/src/parsers/lwc/dom-injection.ts` `detectDomInjection` (line 79). LWC bundle parser stamps `domInjection` on the `LWC` node (`parsers/lwc/bundle.ts` line 131); the Aura parser on the `AuraComponent` node (`parsers/aura/bundle.ts` line 313). Salts: LWC `lwc-attrs:v6`, Aura `aura-attrs:v3`. Read by `scanCodeSecurity`. `file` is the bundle folder URI plus the JS file name.

**Check**: `npx vitest run src/analyze/__tests__/code-checks.test.ts -t "DOM injection|detectDomInjection"` in packages/core. Expect pass: `visitNotes.js` line 18 (high, lwc:dom manual), `visitInsert.js` line 8 (insertAdjacentHTML), `VisitPanelHelper.js` line 4 (Aura), `visitBanner.js` line 7 (low); `visitClean` silent.

**Untested / limits**: `aura:unescapedHtml` markup, `document.write`, `eval`, and `lwc:dom="manual"` with a non-`innerHTML` way of adding nodes are not checked. `lwc:dom="manual"` alone (no `innerHTML`) is not reported, as asked. A data-flow check (is the value actually user-controlled) is not done: any non-literal value is `high`. Re-ingest needed for graphs from before 1.9.0.

## Flow DML in a loop (S-1.9.0-004, D15)

### C-1.9.0-004: `governor.flow-dml-in-loop`

**What**: `governor_risk_check` reports `risk: "flow_dml_in_loop"` against the Flow qname for a `recordCreates`, `recordUpdates` or `recordDeletes` element on a Loop element's iteration path: from the loop's `nextValueConnector`, following every connector (decisions, assignments, fault connectors, nested loops) until it returns to the loop, never through that loop's `noMoreValuesConnector`. Only elements whose path returns to the loop count, so a fault path to a log record that ends the flow is not reported. An element in a nested loop is reported once, against the innermost loop. Extra fields: `element`, `loop`, `line` (the element's opening tag in the Flow XML), plus `ruleId`, `severity: "high"`, `file`, `message`.

**How**: `packages/core/src/analyze/flow-dml-loop.ts` `detectFlowDmlInLoop` (line 75), run in `scanGovernorRisks` (`analyze/governor.ts` line 226) over the stored Flow XML snippet (works on graphs ingested before 1.9.0). The existing `scan` counts in `governor_risk_check` still count methods and triggers only; a flow scan that stopped early makes `scan.complete` false.

**Check**: `npx vitest run src/analyze/__tests__/code-checks.test.ts -t "detectFlowDmlInLoop|Flow DML"`. Expect pass: fixtures `flows/Visit_Close_Tasks` (Update_Task, line 38), `Visit_Branch_And_Nested` (Delete_Sub in Inner_Loop line 47, Create_Log in Outer_Loop line 54); silent: `Visit_Close_Once` (DML after loop), `Visit_Fault_Log` (fault path ends the flow), `Visit_No_Dml`.

**Untested / limits**: subflows and Apex actions inside a loop are not followed (a subflow that does DML is not seen); only the Flow XML's own connectors are read (scheduled paths and screen flows with loops are treated like any other element); Flow versions are judged by the stored XML, active or not.
