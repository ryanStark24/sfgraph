## Async work in a loop (S-1.9.0-001, D02)

### C-1.9.0-001: `governor.async-in-loop`

**What**: `governor_risk_check` reports `risk: "async_in_loop"` for `System.enqueueJob`, `Database.executeBatch`, `EventBus.publish`, `Messaging.sendEmail`, and a call to an `@future` method inside a `for`, `while` or `do` loop body of a method or trigger. Fields added to the risk (all optional): `ruleId` (`governor.async-in-loop`), `severity` (`high`), `file` (the node's `sourceUri`), `line` (file line), `message`. `evidence` is the source line.

**How**: detector `packages/core/src/analyze/apex-code-checks.ts` `detectAsyncInLoop` (line 68), reusing `computeLoopRanges` (the loop logic of the existing in-loop checks) on the comment- and string-masked body. `@future` methods come from the `isFuture` attribute (`futureMethodKeys`, `analyze/governor.ts` line 79); a call matches as `Class.method(` or, inside the same class, `method(`. Wired in `scanGovernorRisks` (`analyze/governor.ts` line 203). Text comes from the method's stored snippet, so it works on graphs ingested before 1.9.0.

**Check**: `cd packages/core && npx vitest run src/analyze/__tests__/code-checks.test.ts -t "async"` (detector cases and the ingest case "governor: async work in a loop"); `cd packages/mcp-server && npx vitest run src/tools/__tests__/code-checks-tools.test.ts`. Expect pass. Fixture `packages/core/src/analyze/__tests__/fixtures/code-checks-project/.../classes/VisitTriggerHandler.cls` (positives at lines 6, 14, 15, 19, 27, 39; negatives `bulkified`, `notAsync`), `triggers/VisitTrigger.trigger` line 3. Expected 7 risks, none for the negatives.

**Untested / limits**: direct only (a loop calling a helper that enqueues is not followed); an `@future` method called through an instance variable (`svc.notify(...)`) is not matched; class-level initialisers are not scanned (only methods and triggers); `Database.executeBatch`/`enqueueJob` inside a lambda or inner-class method are judged per method. Severity is fixed at high; limits per call are not counted (one call in a loop is reported even if the loop is bounded to one iteration).

## Flow DML in a loop (S-1.9.0-004, D15)

### C-1.9.0-004: `governor.flow-dml-in-loop`

**What**: `governor_risk_check` reports `risk: "flow_dml_in_loop"` against the Flow qname for a `recordCreates`, `recordUpdates` or `recordDeletes` element on a Loop element's iteration path: from the loop's `nextValueConnector`, following every connector (decisions, assignments, fault connectors, nested loops) until it returns to the loop, never through that loop's `noMoreValuesConnector`. **How**: `packages/core/src/analyze/flow-dml-loop.ts` `detectFlowDmlInLoop` (line 75), run in `scanGovernorRisks` (`analyze/governor.ts` line 226) over the stored Flow XML snippet (works on graphs ingested before 1.9.0). The existing `scan` counts in `governor_risk_check` still count methods and triggers only; a flow scan that stopped early makes `scan.complete` false.

**Check**: `npx vitest run src/analyze/__tests__/code-checks.test.ts -t "detectFlowDmlInLoop|Flow DML"`. Expect pass: fixtures `flows/Visit_Close_Tasks` (Update_Task, line 38), `Visit_Branch_And_Nested` (Delete_Sub in Inner_Loop line 47, Create_Log in Outer_Loop line 54); silent: `Visit_Close_Once` (DML after loop), `Visit_Fault_Log` (fault path ends the flow), `Visit_No_Dml`.

**Untested / limits**: subflows and Apex actions inside a loop are not followed (a subflow that does DML is not seen); only the Flow XML's own connectors are read (scheduled paths and screen flows with loops are treated like any other element); Flow versions are judged by the stored XML, active or not.

## Review fixes (Codex review of PR #36)

### C-1.9.0-009: Taint kept through `String.valueOf` and `+=`; DOM sinks not matched inside strings

**What**: three false negatives/positives found by review, each reproduced by a failing test first. (1) `String.valueOf(term)` with a String parameter no longer counts as a safe conversion: its argument's taint is propagated (`String.valueOf(5)`, an Integer-typed argument and `String.valueOf(String.escapeSingleQuotes(x))` stay silent; `Integer/Long/Decimal/Double/Boolean/Id/Date/Datetime/Time.valueOf` stay exempt). (2) `term += '%'` on a parameter no longer drops its taint: a parameter loses taint only through a plain assignment that is itself safe (`term = String.escapeSingleQuotes(term)`), and `+=` after such an assignment stays safe. (3) DOM-injection sinks are located on a copy where string literals and template-literal text are blanked (`${...}` expressions kept), so `const example = "el.innerHTML = data";` is not reported; the right-hand side, evidence and line still come from the original text.

**How**: `packages/core/src/parsers/apex/soql-injection.ts` (`SAFE_CONVERSION_RE`, `STRING_VALUEOF_RE`, `variable()` `plain` flag); `packages/core/src/parsers/lwc/dom-injection.ts` (`maskStrings`, used by `detectDomInjection`).

**Check**: `cd packages/core && npx vitest run src/analyze/__tests__/code-checks.test.ts`. New cases: "flags String.valueOf of a String parameter", "a parameter appended to with +=", "a variable appended to with += from a parameter copy", "does not flag safe conversions, a sanitised parameter appended to, or typed arguments", "does not locate a sink inside a string or template text", "still locates a sink in code beside or inside strings...". Before the fix 4 of them fail.

(4) An `escapeSingleQuotes(...)` call exempts only its own result: `String.format(t, new List<String>{term, String.escapeSingleQuotes(other)})` and `a + String.escapeSingleQuotes(b)` still report the unescaped sibling; a fully escaped list, escaped concatenations and binds stay silent (test "an escapeSingleQuotes call exempts only its own result").

**Untested / limits**: still flow-insensitive: a parameter that is escaped only on one branch is treated as escaped. The string masker is a lexer, not a JS parser: regex literals containing quotes are not understood. Comments inside `${...}` are skipped, so an apostrophe there does not open a string. Hash salts are not bumped for these fixes: #34 already moved the salts from their 1.8.2 values (Apex v14, LWC v6, Aura v3) and 1.9.0 is unpublished, so every existing graph is on the 1.8.2 salts and re-ingests with the fixed detectors.

### C-1.9.0-010: Finding `file` has one spelling on Windows and POSIX

POSIX URIs and `sf://` URIs are unchanged. The test's `rel` helper normalises the project root the same way.

**Check**: `cd packages/core && npx vitest run src/analyze/__tests__/code-checks.test.ts -t normalizeSourceUri` (Windows-style path, `file:///C:/` URI, POSIX URI, `sf://`).

### C-1.9.0-013: Typed numeric values stay safe through `String.valueOf`; Flow loop check is linear

**What**: two findings from an outside review of 1.9.0. (A) `security.soql-injection`: a value of a non-text type must not be reported when it goes through `String.valueOf`, `+` or a `String.format` argument. Integer, Long, Decimal, Double, Boolean, Id, Date, Datetime and Time parameters and locals already stayed silent in those shapes; the remaining false positives were a `System.`-prefixed type (`System.Integer n`) and a number read out of a map (`Map<String, Integer> caps`, `caps.get(k)`). Both are now safe. A String parameter through `String.valueOf`, `+ ''` or `String.format` is still reported, and so is a `Map<String, String>` read. (B) `governor.flow-dml-in-loop`: the "path returns to the loop" step re-scanned every element until nothing changed, which is quadratic on a long chain, and the element line was found by scanning the XML once per DML element. It now walks the reversed connectors once from the loop, computes each element's connector targets once, and finds all DML lines in one pass. Results are identical (existing tests unchanged). No hard cap was needed.

**How**: `packages/core/src/parsers/apex/soql-injection.ts` (`SAFE_TYPE_RE`, `SAFE_GENERIC_RE`, `SAFE_MAP_VALUE_RE`, `MAP_READ_RE`); `packages/core/src/analyze/flow-dml-loop.ts` (`targetsFor`, reverse walk, `dmlLines`).

**Check**: `cd packages/core && npx vitest run src/analyze/__tests__/code-checks.test.ts`. New cases: "typed non-String values through String.valueOf, format and +" (9 types x 8 shapes, plain and `System.`-prefixed; Map values; a String still flagged) and in `detectFlowDmlInLoop` "analyses a 16,000-element loop body in linear time and still finds the DML" (asserts under 2 s) and "finds the line of every DML element in a flow with thousands of them". Before the fix (all of A, 013a-c): 83 fail (the `System.`/Map shapes and the 16,000-element chain, 52 s here); after: 296 ms.

**013a (String.format arguments)**: `String.format` now judges each argument expression (a `new List<String>{...}` element by element) with the normal rules, instead of scanning identifiers, so `String.valueOf(Integer.valueOf(term))`, `Long/Decimal/Double/Boolean/Id/Date.valueOf(term)`, `escapeSingleQuotes(term)` and describe names are safe for their own argument only; a sibling `term` is still reported.

**013b (assignment order)**: assignments are applied in source order up to each query call, and the last definite assignment wins, so `String value = term; value = String.escapeSingleQuotes(value);` is no longer reported. Definite means at the method body's own brace depth and not the body of a braceless `if`/`else`/`for`/`while`. Conditional rule: a tainted value stays tainted through any conditional assignment; a conditional safe assignment clears only a parameter's own text (unchanged rule: a parameter escaped inside a branch counts as escaped). An assignment after the query call no longer counts.

**013c (alias chains, isolation)**: the variable analysis was recursive; a 2000-alias method (41.9 KB) overflowed the stack, the parser threw and ingest dropped the whole class. It is now a single forward pass over the assignments (no recursion), and `soqlInjectionAttr` (`class.ts`, used for methods and triggers) catches any checker failure so it loses only that attribute. Tests: "handles a 2000-alias chain without a stack overflow" and `parsers/apex/__tests__/soql-injection-isolation.test.ts` (class still parsed, finding still reported).

**013d (Codex review of #43)**: (1) a query call inside an assignment's own right-hand side (`q = String.valueOf(Database.countQuery(q))`) is checked against the state before that assignment, which is applied afterwards; (2) a `new List<String>(terms)` argument of `String.format` is judged by its constructor arguments (safe only if every argument is); (3) loop-carried taint: for a call inside a for/while/do body (braced or not), any tainting assignment anywhere in the enclosing loop body counts, even after the call, and a later safe reassignment never clears it (conservative: `q = escape(q); query(q); q = term;` in a loop is reported). Tests: "checks a query call inside an assignment's own right-hand side...", "inspects the arguments of a copy constructor...", "carries taint around a loop..." (3 fail on the previous commit).

**013e (second Codex review of #43)**: (1) `x[...]` on a tainted collection is tainted like `x.get(...)` (this also closes the 1.9.0 gap "bracket indexing `terms[0]` does not carry taint"; a `List<Integer>` stays safe); (2) assignments in the condition and update clauses of a `for (init; cond; update)` header are conditional. The init clause stays definite: it always runs exactly once. Tests: "carries taint through indexed access...", "treats the condition and update clauses of a for header as conditional".

**013f (design change after four more Codex findings; supersedes the flow rules in 013b and 013d)**: the analysis is monotone against the parent. The default is the parent's flow-insensitive rule (a variable is tainted if it is a parameter that was not replaced, or any assignment to it anywhere carries taint; alias chains are followed with a worklist, no recursion). A finding that rule reports is dropped only in the provably simple case: the call is outside every loop (for/while/do, header and body), every assignment to the variables the argument reads and to the ones they were copied from is a straight-line statement at the body's own brace depth (not in a branch, braceless if/else, loop, any parenthesis such as a for header or a condition), and the source-order value at the call is safe. Everything else, including loop-carried, for-header, while-condition and reverse-order alias cases, keeps the finding by construction. Redundant parentheses around a String.format argument or `new` expression are removed before inspection. The loop-overlay and conditional-clear machinery of 013b/013d is gone; the "parameter escaped inside a branch counts as escaped" rule is the parent's, unchanged. Differential test `parsers/apex/__tests__/soql-injection-differential.test.ts` runs a corpus (the earlier cases and the Codex cases) through a verbatim copy of the parent (`_soql-injection-parent.ts`, bb00bc5) and requires new to report everything the parent did, except the allow-list: numeric-valueOf, straight-line-sanitizer, typed-param, describe-per-argument, map-value; the one intended addition is `terms[0]` indexed access.

**013g (Codex finding 4579063957)**: a `String.format` argument that is a ternary of collections (`flag ? new List<String>{ term } : new List<String>{ 'x' }`), parenthesised, nested or cast is inspected branch by branch and element by element. Sweep: the only place the new code judged an expression safe without looking inside a `new` was `String.format` arguments (everywhere else `new` was already treated as the parent did). Any `new` expression the collection rules do not understand (`new X{...}.clone()`, `Helper.pick(new List<String>{ term })`, `new Foo(term).name`) now falls back to the parent's view: a tainted variable named inside it, minus `escapeSingleQuotes` arguments, taints it. All added to the differential corpus.

**013h (two more Codex findings; structural)**: (1) the dependency closure used by the "drop a finding" step is a plain scan of identifiers in each right-hand side's text (`Assignment.ids`), never the reads of an evaluation, so short-circuiting cannot hide a dependency (`b + c` with `c` conditionally cleared is reported); the worklist uses the same lexical dependencies. (2) `operand` now treats an expression as safe only when it matches a known-safe shape exactly: a whole literal or number, a numeric `.valueOf(...)` whose paren ends the expression (or is followed only by no-argument calls), an `escapeSingleQuotes(...)` wrapper whose paren ends it, a describe chain, a safe-typed variable, a numeric member call after the ternary split. Anything else is read by the parent's rule (a tainted variable named anywhere in the text, outside `escapeSingleQuotes` arguments). So `String.valueOf(term).trim()`, `(String) term`, `new X{...}` outside format arguments, and `flag ? term : list.size()` are reported. (3) Final guard: before a finding is dropped, every variable in the lexical closure must have only straight-line assignments, none inside a loop. Differential corpus gained the two Codex cases and a generated 6 shapes x 8 assignment patterns grid (monotone against the parent except the allow-listed straight-then-safe pattern). Intended additions over the parent (true positives it missed), listed in the test as `MORE`: `terms[0]`, a list variable built from `new List<String>{ term }`, a describe call beside an unescaped format argument, `String.valueOf(term).trim()`, `flag ? term : list.size()`, `(String) term`. An undeclared root (`Helper.pick(term)`, constants) is still not judged, as in the parent.

**013i (Codex 4579134683; text-level backstop)**: before any finding the parent's rule reports is dropped, a pure lexical check runs: the sink argument's text is flattened through the effective assignments (last plain assignment before the call and every `+=` after it) of the variables it names, the exact allow-listed safe substrings are blanked (`escapeSingleQuotes(...)` calls, numeric `.valueOf(...)` calls, `Schema` describe chains, literals), and if a parameter the parent's rule leaves tainted is still named in what is left, the finding is kept. No evaluation is involved, so an `operand` rule that wrongly judges a shape safe can no longer drop a finding. Separately, a method call on any receiver is now read by its arguments (`fixed.replace('fixed', term)`, `Helper.pick(term)`, `'abc'.left(term)`); more true positives than the parent, listed as `MORE` in the differential test. The grid gained three method-argument shapes (literal receiver, local receiver, static helper).

**Untested / limits**: other numeric holders (`Map<K, List<Integer>>`, a numeric field of an SObject parameter such as `String.valueOf(acc.NumberOfEmployees)`) are still judged by the parameter's own type and may be reported. The 16,000-element timing is one machine (Linux container); the bound in the test is generous. Nested loops are still walked once per loop. The stored `soqlInjection` attribute is derived by the same detector at parse time, so a graph ingested earlier keeps old results until re-ingested; hash salts are not bumped (the 1.9.0 salts already moved from 1.8.2 and the release is unpublished).
