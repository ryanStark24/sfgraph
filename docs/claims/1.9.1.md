## Rebuild backups (S-1.9.1-001a, 001b)

### C-1.9.1-001: rebuild backups are pruned after the sync completes, never inside `applyRebuild`

**What**: `applyRebuild` (`packages/cli/src/commands/ingest.ts`) only moves the old graph to `backups/<orgId>.rebuild-<stamp>.sqlite`; it no longer prunes. `finishRebuild` runs after the rebuilt graph's sync completed (single org: after `liveIngest`, its pre-sync snapshot and the transient-skip exit-code check; multi-org: for each entry with status `ok`; `--project`: after `liveIngest`, and after the delta full-rebuild callback) via `settleRebuilds`. A sync that exits 1 because `SFGRAPH_SKIP_THRESHOLD` transient sources were skipped does not count as finished: nothing is pruned and the pending marker stays.

**How**: `finishRebuild` clears `<dataDir>/<orgId>.rebuild-pending.json`, then `pruneOrgBackups` (`packages/cli/src/commands/rebuild-backups.ts`) keeps the newest `rebuildBackupsKept()` complete backups (`SFGRAPH_REBUILD_BACKUPS_KEPT`, default 1, from `packages/core/src/storage/retention.ts`; read by `envNonNegativeInt`). The carry of snapshot history (`carrySnapshots`, unchanged) still runs in `buildOnStore` before anything is pruned, so keep 0 still carries.

**Check**: `cd packages/cli && npx vitest run src/__tests__/rebuild-retention.test.ts src/__tests__/rebuild.test.ts src/commands/__tests__/ingest-project.test.ts`. Tests: "nothing is pruned while the sync is failing, however many rebuilds are retried" (3 stub backups + a failing rebuild = 4 backups), "with the default of 1 an older complete backup goes after a good rebuild", "SFGRAPH_REBUILD_BACKUPS_KEPT=0 still carries the snapshot history, then keeps no backup" (new graph has 2 snapshots, no backup left). Expect pass.

**Untested / limits**: `settleRebuilds` in the multi-org branch (`--orgs`, `--all`) has no test of its own; it shares `finishRebuild` with the single-org path, which is tested. The Windows rename of the graph file (existing `onGraphFile`) is unchanged and untested here. Two existing tests changed: `rebuild.test.ts` "two history-less backups..." now passes `{ keep: 2 }` and uses a valid 15-character org id (the new code only treats names with a valid org id as backups), and `ingest-project.test.ts` "final review core I-2" now expects 1 backup instead of 2.

### C-1.9.1-002: a failed rebuild and its retry cannot delete the only good backup

**What**: every `--rebuild` writes `<dataDir>/<orgId>.rebuild-pending.json` when it starts (`markRebuildPending`) and removes it only in `finishRebuild`. A rebuild that starts while the marker exists is moving a half-built graph, so its backup gets a `<backup>.incomplete` marker (`markBackupIncomplete`). `planBackupKeep` never counts incomplete backups toward `keep`; if no complete backup exists, the newest one is kept so something is left (keep above 0).

**How**: `rebuild-backups.ts` `planBackupKeep`, `listBackups` (reads the marker into `BackupSet.incomplete`), `removeBackupSet` (removes sidecars and marker with the backup).

**Check**: `cd packages/cli && npx vitest run src/__tests__/rebuild-retention.test.ts -t "failed rebuild and its retry|planBackupKeep"`. The first test: good graph with 1 snapshot, rebuild with a failing sync (1 backup, marker present), rebuild again failing (2 backups, the second has `.incomplete`), rebuild succeeding: only the first (good) backup remains, the marker file is gone, and the new graph holds the carried snapshot. Expect pass.

**Untested / limits**: a graph left half-built by a failed rebuild and then completed by a plain `sfgraph ingest` (not `--rebuild`) keeps the pending marker, so the next rebuild marks its backup incomplete although it was complete. The effect is only that it does not count toward the backups kept (and is removed after the next good rebuild if a complete one exists); with no complete backup the newest is still kept. A carry always reads from the newest backup: if that backup is an incomplete one without history, history held only by an older complete backup is not carried (that backup is then kept by the history rule, see C-1.9.1-003).

### C-1.9.1-003: the backup holding snapshot history is kept when the carry failed

**What**: with `protectHistory` (set when the rebuild's carry copied 0 snapshots, and always for the cross-org sweep) the newest complete backup with snapshot history (`snapshotCountInFile` not 0; unreadable = -1 counts as holding) is kept in addition to the newest `keep`.

**How**: `planBackupKeep(sets, keep, protectHistory, historyOf)`; `finishRebuild` passes `protectHistory: run.carried === 0`.

**Check**: `npx vitest run src/__tests__/rebuild-retention.test.ts -t "failed carry|planBackupKeep"` and `src/__tests__/rebuild.test.ts -t "keeps the snapshot history"`. The "failed carry" test makes `copySnapshotsFrom` throw, sets keep 0, and expects the one backup with 2 snapshots to remain while the new graph has 0. Expect pass.

**Untested / limits**: when the carry succeeded, the old backup is not protected even if it is the only copy of history that was not carried (nothing was left uncarried by definition).

### C-1.9.1-004: cross-org sweep

**What**: after a finished rebuild, `sweepOtherBackups` (`ingest.ts`) calls `sweepBackups` (`rebuild-backups.ts`), which applies the keep rule (with history protection) to every other org found in `backups/`. For each org it takes the org's ingest lock (`acquireIngestLock`); an org whose lock is held (including by another org of the same run still working) is skipped and reported. Entries in `backups/` that do not match `<orgId>.rebuild-<ISO stamp>.sqlite` (and their sidecar and marker names) are returned as `other` and printed as "not touched"; the sweep never deletes them. A file whose `unlink` fails with `EBUSY`, `EPERM` or `EACCES` is returned in `inUse`, printed "skipped (in use)", and adds nothing to the freed bytes.

**How**: `listBackups`, `removeBackupSet` (main file first; on an in-use error nothing else of that backup is touched).

**Check**: `npx vitest run src/__tests__/rebuild-retention.test.ts -t "trims other orgs|sweepBackups|in use"`. Expect: org A's 3 backups become 1 (the newest, its `-wal` sidecar gone); the locked org keeps its 3; `readme.txt`, a directory and a `rebuild-bogus.sqlite` file stay; the sweep leaves no lock file; the injected `EBUSY` backup stays, `freedBytes` counts only the deleted one.

**Untested / limits**: real Windows `EBUSY` behaviour (simulated only). An org id that is not a valid 15/18-character id or alias (`validateOrgIdentifier`) is not recognised as a backup at all.

## Auto snapshot retention (S-1.9.1-001c)

### C-1.9.1-005: newest N auto snapshots stay, age applies only beyond N, manual snapshots never go

**What**: `SqliteSnapshotStore.pruneAuto(orgId, { keep, retainDays })` (`packages/core/src/storage/sqlite/snapshot-store.ts`) deletes the auto snapshots that `selectAutoToPrune` (`storage/retention.ts`) picks: rows with `is_auto = 1`, newest first by `created_at` then `seq`, skipping the first `keep`, then (when `retainDays` is above 0) only those older than `retainDays` days. `liveIngest` calls it at the end of every sync with `snapshotsKept()` and `snapshotRetainDays()` (`SFGRAPH_SNAPSHOTS_KEPT` default 5, `SFGRAPH_SNAPSHOT_RETAIN_DAYS` default 30) or `LiveIngestOpts.snapshotsKept` / `snapshotRetentionDays`. A failure is logged and does not fail the sync (the existing try/catch). The old behaviour (delete auto snapshots older than 30 days, no count) is replaced. `snapshot prune --retain-days` (`SqliteSnapshotStore.prune`) is unchanged for users.

**Reading of the rule to confirm**: "keep newest N; age limit only beyond those N" was implemented as: beyond the newest N, a snapshot goes only when it is also older than the age limit, and 0 days means no grace (all beyond N go). With the defaults (5 and 30) a graph synced often keeps more than 5 auto snapshots until the extras are 30 days old. `storage clean --snapshots` ignores age (pure count). If the intent was "at most N regardless of age", set `SFGRAPH_SNAPSHOT_RETAIN_DAYS=0` or change `DEFAULT_SNAPSHOT_RETAIN_DAYS` in `retention.ts`.

**Check**: `cd packages/core && npx vitest run src/storage/__tests__/snapshot-retention.test.ts src/ingest/__tests__/live-ingest.test.ts`. Tests: "keeps manual snapshots and the newest N auto ones; age applies only beyond N" (8 auto of ages 0 to 70 days plus 2 manual, keep 5 / 30 days: the three oldest go, the 40-day-old one inside the newest 5 stays), "a snapshot beyond N that is younger than the age limit stays; 0 days removes it", "keep = 0 ... never a manual one", the liveIngest test (6 old auto + 1 manual, keep 2, 0 days: manual + the new pre-sync snapshot + the newest old one remain). Expect pass.

**Untested / limits**: `SFGRAPH_*` env parsing is tested through `envNonNegativeInt` only, not through a full CLI run. `snapshot_create` with `kind: "scheduled"` being pruned is covered by the `is_auto` flag, not by an MCP test. The CLI `snapshot create --kind scheduled` still stores `is_auto = 0` (it always did), so it is treated as manual.

### C-1.9.1-006: batched deletion, identical diffs

**What**: `SqliteSnapshotStore.deleteSnapshots(ids)` deletes several snapshots in one `BEGIN IMMEDIATE` transaction. Per org it garbage-collects version rows once for the batch (rows visible at a deleted seq and at no remaining snapshot) and reopens (`to_seq = NULL`) the rows closed after the org's newest remaining snapshot, once. `deleteSnapshot(id)` is now `deleteSnapshots([id])`. The visible-at-a-deleted-seq filter is a `json_each` over the batch's seqs, so each version table is scanned once per org, not once per snapshot.

**Check**: `npx vitest run src/storage/__tests__/snapshot-retention.test.ts -t "point_in_time_diff|batch delete|second sync"` plus the existing `snapshot-store.test.ts` and `snapshot-versions.test.ts`. "point_in_time_diff between kept snapshots is identical before and after pruning": 10 auto snapshots with node and edge changes and a deleted node; `diffNodes`, `diffEdges` and `diffEdgesPage` for every ordered pair of the 4 newest snapshots and `current` are deep-equal before and after pruning 6. "a batch delete leaves the same version rows as deleting one by one": a `VACUUM INTO` copy has the same snapshots deleted one at a time (including the newest) and the version tables, and snapshot seqs are equal. "a second sync after pruning reuses the freed pages": after `pruneAuto`, `freelist_count` is above 0 and `page_count` is unchanged (pruning does not shrink); another sync-sized change plus snapshot does not raise `page_count`. Expect pass.

**Untested / limits**: timing was not measured (no benchmark on a multi-GB graph); the claim is structural (one scan per org instead of one per snapshot). Not run against the owner's real 8.2 GB graph.

## `sfgraph storage` (S-1.9.1-001e)

### C-1.9.1-008: `sfgraph storage` is read-only and fast

**What**: `storageCmd` / `buildStorageReport` (`packages/cli/src/commands/storage.ts`) lists `<dataDir>/<orgId>.sqlite` files, opens each read-only (`readonly: true`, 500 ms busy timeout, never migrating), and reads page counts, snapshot counts (`_sfgraph_snapshots` grouped by `is_auto`), alias and `last_synced_at` (`_sfgraph_orgs`). `stale` uses the `list_orgs` rule (never synced, or 7 or more days). A read-only open of a WAL-mode file leaves empty `-wal`/`-shm` files behind; `openReadonly` removes them on close when neither existed before (and the `-wal` is empty), so a report or a dry run leaves the directory byte-identical. A graph that cannot be opened or read still reports `bytes` and `walBytes`, with `snapshots: { auto: null, manual: null }`, `freeBytes: 0`, `lastSyncAt: null`, `stale: true`. `--detail` adds `tables` (largest 25 by `dbstat`); without it dbstat is never read.

**Check**: `cd packages/cli && npx vitest run src/commands/__tests__/storage.test.ts -t "report"`. Expect: sizes, snapshot counts (8 auto, 1 manual), alias, stale flags, backups per org with `newestAt`, `other` for a hand-made file, embedding cache 4000 bytes, the directory hash unchanged by the report, an unreadable file reported with null counts, `--detail` tables present. Try it: `node apps/sfgraph/bin/sfgraph.mjs storage` and `storage --json`.

**Untested / limits**: speed was not measured on a large data dir (it stats files and runs three small queries per graph). A graph that is exclusively locked by another process was only simulated by a non-database file. `dbstat` availability depends on the SQLite build; if absent `tables` is omitted.

### C-1.9.1-009: JSON shape (schemaVersion 1)

```
{ schemaVersion: 1, dataDir, totalBytes,
  graphs: [{ orgId, alias: string|null, file, bytes, walBytes, freeBytes,
             snapshots: { auto: number|null, manual: number|null },
             lastSyncAt: string|null, stale: boolean, tables?: [{ name, bytes }] }],
  backups: { count, bytes, byOrg: [{ orgId, count, bytes, newestAt: string|null }], other: { count, bytes } },
  embeddingCache: { bytes }, otherBytes }
```

`file` is the absolute graph path. `bytes` is the file only, `walBytes` the `-wal`, `totalBytes` the whole data dir. `backups.bytes` counts rebuild backups with their sidecars and markers; `backups.other` is everything else in `backups/`. `otherBytes` is `totalBytes` minus graphs (file plus wal), backups, `backups/` extras and the embedding cache (so it includes `-shm` files, locks, `.sfgraph-backups/`, exports, skip reports).

**Check**: `npx vitest run src/commands/__tests__/storage.test.ts -t "JSON shape"` (inline snapshot with numbers masked, `schemaVersion` kept as 1).

### C-1.9.1-010: `storage clean` is a dry run unless `--apply`

**What**: `runClean` plans every action and executes only with `apply`. No category flag = backups + snapshots, never vacuum. `--backups`: all rebuild backups of all orgs or `--org`; other files in `backups/` are listed as `other-file`, status `planned` and detail "only removed with --backups", and are removed only with `--backups --apply`. `--snapshots [--keep n]`: `pruneAuto` with the given keep (default `snapshotsKept()`) and no age grace. `--vacuum`: see C-1.9.1-011. Result `{ schemaVersion: 1, applied, actions: [{ kind, orgId, path?, bytes, status, detail? }], freedBytes }`, `freedBytes` summed from actions with status `done` (backups: bytes removed; snapshots and vacuum: file+wal size before minus after). Exit code (`exitCodeFor`): 1 when an action failed, 3 when any action is `skipped-busy` or `skipped-in-use`, else 0 (`skipped-low-disk` alone exits 0). `--org` takes an org id, a 15-character prefix of an 18-character id, or the alias stored in a graph; an unknown name throws (exit 1). A live graph file is never deleted by `clean`.

**Check**: `npx vitest run src/commands/__tests__/storage.test.ts -t "clean|wiring"`. "without --apply changes nothing, whatever the flags" hashes the whole data dir (names, sizes, content) before and after five flag combinations, including `--vacuum`; "--apply default" removes the backups and prunes to `--keep 2` while keeping the manual snapshot, `notes.txt` and both graphs, and leaves no lock files; "a held ingest lock skips that org (exit 3)"; "a backup the OS reports in use is skipped"; "wiring": `storage clean --json`, `storage --json`, `storage drop alpha --json` each get their own `--json` (needs `program.enablePositionalOptions()` on the root and on `storage`; without it commander gives `--json` to the parent).

**Untested / limits**: `--keep` on `--backups` is not a thing (it only applies to snapshots). A snapshot prune of a graph that needs a schema migration runs the migration (it opens the graph through `SqliteGraphStore`, like `snapshot` commands do), which may write a pre-migration backup under `<data-dir>/.sfgraph-backups/`.

### C-1.9.1-011: `--vacuum` shrinks, and refuses when it cannot do so safely

**What**: `SqliteGraphStore.compactFile` (`graph-store.ts`) runs `wal_checkpoint(TRUNCATE)`, `VACUUM`, `wal_checkpoint(TRUNCATE)`; it throws "WAL busy" before `VACUUM` when another connection prevents the checkpoint, so the file is untouched. It sets `temp_store = FILE` around `VACUUM` (the connection normally keeps temp data in memory, which on a multi-GB graph would need that much RAM) and restores it. `compactAfterPurge` now reuses it (the purge path is otherwise unchanged). `storage clean --vacuum` checks free disk (`statfsSync`, injectable) against twice the file size first: below that the action is `skipped-low-disk` and nothing runs; "WAL busy" becomes `skipped-busy`; a graph with no free pages is `done` with "no free pages to give back" without running `VACUUM`. It sets `busy_timeout = 250` first so a second connection refuses the vacuum instead of stalling it.

**Check**: `npx vitest run src/commands/__tests__/storage.test.ts -t "vacuum"` and `cd ../core && npx vitest run src/ingest/__tests__/custom-setting-rows-disk.test.ts`. "shrinks a file with free pages": after pruning to 1 snapshot the file is smaller, the vacuum action's `bytes` equals the size difference, `freeBytes` is 0 afterwards. "skipped while another connection holds a read transaction": a second connection in `BEGIN` + read makes the action `skipped-busy`, exit 3, file size unchanged. "refused when free disk is below twice the file size": `freeDiskBytes: () => size*2 - 1` gives `skipped-low-disk` and an unchanged file; `size*2` runs it. Expect pass.

**Untested / limits**: not run on a multi-GB file (time and peak disk use are not measured; free-space check is the only guard). The disk check uses the data dir's volume; a graph reached through a symlink on another volume is not accounted for. On a graph held open by `sfgraph serve` in WAL mode a checkpoint may succeed while readers idle, so the vacuum can run while a server has the file open; stop servers first (documented).

### C-1.9.1-012: `storage drop <org>`

**What**: `runDrop` resolves the name with `resolveLocalOrg` (graph file names, backup org ids, aliases stored in graphs; an unknown name throws), then under the org's ingest lock deletes the graph file and its `-wal`/`-shm`/`-journal`, then every rebuild backup of the org with their sidecars, then the pending-rebuild marker. A dry run lists them as `planned` (graph action `kind: "graph"`). A held lock: all actions `skipped-busy`, nothing removed. If the graph file itself is in use (`EBUSY`/`EPERM`/`EACCES`) its backups are left too. An org with only backups left can be named by id. Not removed: `<orgId>.skips.json`, entries in `exports/`, the shared embedding cache.

**Check**: `npx vitest run src/commands/__tests__/storage.test.ts -t "drop"`: refuses `gamma` without changing the directory hash; dry run changes nothing; `--apply` removes `00Dxx0000001aaa.sqlite`, its `-wal`, pending marker, both backups and a backup `-wal`, and leaves the other graph, the other org's backup and `notes.txt`; busy lock skips everything.

**Untested / limits**: on macOS and Linux deleting a graph that `sfgraph serve` holds open succeeds (the server keeps the unlinked file until it exits); only the lock protects against a running ingest. Windows in-use handling is simulated only in the backup path, not for the graph file.
