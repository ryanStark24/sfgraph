# Request ledger: sfgraph 1.9.1

Every ask for 1.9.1 is logged here before it is built: the requester's words, acceptance criteria and status. Claims (what was done and how to check it) live in [../claims/1.9.1.md](../claims/1.9.1.md). The format follows [1.9.0.md](1.9.0.md).

Source of the ask: the owner's report from a Mac whose sfgraph data dir had grown to 53 GB. 1.9.0 is unreleased; this ships as patch 1.9.1 (no version bump or release section yet: release prep is a later step).

**Exact ask (the owner's report):** "sfgraph storage: why it's 53 GB … rebuild backups pile up ~30 GB, pre-sync snapshots ~6 GB in graph A, stale graphs kept; I didn't find a retention or cleanup setting".

What was found on that machine: `backups/` held 42 full graph copies (~30 GB); an old stale org had 12 backups from June that never went, because pruning only ran for the org being rebuilt. One live graph was 8.2 GB with ~5.8 GB of snapshot version tables from 10 automatic pre-sync snapshots, which nothing pruned except the manual `sfgraph snapshot prune`. About 1.1 GB of free pages sat in one file because nothing ever reclaimed them.

| S-1.9.1-001a | owner report | P1 | Rebuild backups: keep 1 per org, prune only after a successful rebuild. | Default keeps the newest 1 backup per org (`SFGRAPH_REBUILD_BACKUPS_KEPT`, integer 0 or more; anything else falls back to 1). Pruning is not done by `applyRebuild`; it runs after the rebuilt graph's sync completed and its pre-sync snapshot was taken. A failed rebuild followed by a retry never deletes the only good backup: a backup of a graph whose rebuild never finished is marked incomplete and never counts toward the ones kept. With keep 0 the snapshot history is still carried into the new graph before the backup goes. When the carry failed, the newest backup that holds snapshot history is kept (unreadable counts as holding). | Built | |
| S-1.9.1-001b | owner report | P1 | Cross-org sweep of rebuild backups. | After a successful rebuild the same keep rule is applied to every org's `<orgId>.rebuild-<stamp>.sqlite` files in `backups/`, with their sidecars. An org whose ingest lock is held is skipped. Files that do not match the pattern are reported and never touched. A file that cannot be deleted because it is in use (Windows EBUSY/EPERM/EACCES) is reported "skipped (in use)" and not counted as freed. | Built | |
| S-1.9.1-001c | owner report | P1 | Auto snapshot retention. | After each sync the newest `SFGRAPH_SNAPSHOTS_KEPT` (default 5) auto snapshots per org stay (auto = `is_auto = 1`, which includes `snapshot_create` with `kind: "scheduled"`). Every older auto snapshot goes (owner decision: pure keep-newest-N by default); `SFGRAPH_SNAPSHOT_RETAIN_DAYS` (default 0) is an optional age floor for snapshots beyond N. Manual snapshots are never pruned automatically. A prune error does not fail the sync. Deleting several snapshots does one version-row garbage collection per org in one transaction (`deleteSnapshots`). `point_in_time_diff` between snapshots that stay returns identical results before and after pruning. | Built | |
| S-1.9.1-001d | owner report | P1 | No VACUUM inside ingest; say when it would help. | Ingest never runs `VACUUM`. After pruning, if an org's free pages exceed 256 MB, one line is printed: `reclaimable <X> GB in <orgId>: run "sfgraph storage clean --vacuum"`. | Built | |
