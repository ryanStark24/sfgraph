# Request ledger: sfgraph 1.8.2

Every ask for 1.8.2 is logged here before it is built: the requester's exact words, acceptance criteria, the owning thread, and status. Every merged PR maps to an entry. Before publishing, a fresh, independent agent with no build context checks each entry against the built packages; any Fail blocks the release. Claims (what was done and how to check it) live in [../claims/1.8.2.md](../claims/1.8.2.md).

Source of the findings: the independent 2026-11-14 code and delivery audit of sfgraph 1.8.1 at master `ad4afd0`, copied to [../audit/2026-11-14-audit.md](../audit/2026-11-14-audit.md). Its three reproduction runners are in [../audit/2026-11-14-evidence/](../audit/2026-11-14-evidence/); on `ad4afd0` (Linux, Node 22) all three print their `..._CONFIRMED` line, so every reproduced finding below was seen before fixing.

**Exact ask (the maintainer, 2026-11-14):** "okay we got issues" (with the audit attached).
**Scope given to the thread:** fix all four P1s; fix the small P2s F06, F07, F09, F10, F11, F12, F13; bump Zod if it is easy (F08); record F05, F08 (rest), F14 to F18 as backlog with notes. Every fix has a test through the real CLI or MCP entry point that would have caught it. No Salesforce org is contacted. Publishing to npm is the maintainer's step only, after an independent re-audit passes.

Owner thread for every entry: "Fix sfgraph audit issues for 1.8.2".

| S-1.8.2-001 | F01 | P1 | The read-only Salesforce wrapper really is read-only. | Live extraction gets a small typed read facade (only the read calls sfgraph uses), never a raw jsforce object or a bound arbitrary SDK function; no `_conn` or other back-reference reaches the raw connection. A transport-level guard on the real jsforce `Connection` refuses every write request (POST/PATCH/PUT/DELETE) except an explicit allow-list of read protocols that use POST (for example Metadata API `readMetadata`/`listMetadata`/`describeMetadata` SOAP, retrieve-free Tooling/composite reads if used).
