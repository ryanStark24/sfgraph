# sfgraph code and delivery audit

14 November 2026 · Repository: [ryanStark24/sfgraph](https://github.com/ryanStark24/sfgraph)

**Verdict: changes required before treating sfgraph as a security boundary or using its results as sufficient evidence for deletion or deployment.** The implementation is substantial and its current regression suite passes. Important gaps remain in the read-only guarantee, deployment correctness, live synchronization, and completeness of audit answers.

Audited default branch `master`, release `1.8.1`, commit [`ad4afd088d87e2565eada89a9b58d62c21977fd4`](https://github.com/ryanStark24/sfgraph/commit/ad4afd088d87e2565eada89a9b58d62c21977fd4). Source was cloned separately to `/tmp/sfgraph-audit-20261114`. No application source was changed, no issues or reviews were posted, and no Salesforce org was contacted or modified. Write-request reproductions intercepted the SDK transport locally.

## High-priority findings

### F01 — P1: the read-only Salesforce wrapper permits real write requests

**Evidence:** [read-only-proxy.ts:103](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/extractors/live-org/read-only-proxy.ts#L103), [generic surface wrapper:223](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/extractors/live-org/read-only-proxy.ts#L223). Reproduced using the installed jsforce `3.10.15`, with its transport replaced by a local recorder.

The generic wrapper uses a method-name denylist and binds permitted functions to the raw object. `post` and `patch` are absent from that denylist. The specialized SObject and Metadata wrappers also expose their `_conn` reference.

These operations passed the wrapper and reached the intercepted transport:

```js
await wrapped.apex.post('/audit-only', { name: 'no-network' });
await wrapped.sobject('Account')._conn.create('Account', { Name: 'no-network' });
wrapped.metadata._conn === rawConnection; // true
```

The first two produced POST requests. Nothing was sent to Salesforce. I did not identify an intentional Salesforce write in the shipped ingestion workflow; this finding concerns the advertised enforcement boundary and protection against accidental or future write calls.

**Fix:** expose a small, typed capability facade containing the read operations sfgraph actually needs. Do not expose raw objects or bind arbitrary SDK functions to them. Intercept at an appropriate transport boundary while explicitly allowing the POST-based read protocols Salesforce requires; simply banning every HTTP POST would break legitimate reads. Verify the real SDK surfaces, returned handles, and back-references, in addition to mocks. Revise the absolute privacy/security claim until the boundary is enforced.

### F02 — P1: case-only name differences generate a destructive deployment entry

**Evidence:** [cross-org.ts:124](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/analyze/cross-org.ts#L124), [generate.ts:170](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/analyze/deployment-manifest/generate.ts#L170). Independently reproduced with two real SQLite graph stores.

The storage layer handles qualified names without ASCII case sensitivity, but the cross-org diff builds JavaScript Maps using the original strings. Source `ApexClass:BillingService` and target `ApexClass:billingservice`, with identical source hashes, become one addition and one removal. The manifest includes `billingservice` under `ApexClass` in `destructiveChanges.xml`, while reporting neither truncation nor unmapped content.

**Impact:** a logically identical component can be proposed for removal rather than recognized as the same component. The generated files can be destructive or invalid; no deployment was attempted in this audit.

**Fix:** use the same canonical comparison key across storage, cross-org comparison, and manifests, preserving original case for display. Add a final invariant that a logical component cannot appear in both deployment and deletion output. Verify case-only classes, fields, methods, and namespaced metadata.

### F03 — P1: default live incremental sync does not refresh changed content

**Evidence:** [mode selection:713](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/ingest/live-ingest.ts#L713), [incremental implementation:1190](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/ingest/live-ingest.ts#L1190), [SourceMember type filter:62](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/extractors/live-org/source-member.ts#L62). Independently reproduced through `liveIngest`, with mock Salesforce responses and a real store.

After an initial sync, `auto` chooses incremental mode when source tracking is available. That branch applies deletions but explicitly does not fetch or parse additions and modifications. A changed Apex class retained its old source hash and processed zero members. The warning and held watermark are useful safeguards, but they do not deliver an updated graph.

A second problem is less visible: SourceMember types outside its small map are discarded. A Workflow change was ignored, no `contentNotFetched` warning was returned, and the sync watermark advanced. The README advertises fast subsequent incremental sync without describing these functional limits.

**Fix:** fetch current member content and re-run the relevant parsers/resolvers, including container handling for child metadata. Until that exists, make `auto` fall back to a full refresh when changes are detected and expose unsupported change types as incomplete work. A fresh timestamp must not imply that ignored metadata was refreshed. Keep filesystem `--delta` separate: it is implemented and is not the missing feature described here.

### F04 — P1: audit scan caps can produce a false “no findings” answer

**Evidence:** [dead-code.ts:300](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/analyze/dead-code.ts#L300), [governor.ts:93](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/analyze/governor.ts#L93), [dead-code result:404](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/mcp-server/src/tools/dead_code_audit.ts#L404). Independently reproduced with generated SQLite data and the MCP dispatcher.

The scored dead-code scan reads only the first 10,000 nodes per supported label. A pattern filter is applied afterward. With 10,001 unreferenced classes, `dead_code_audit(pattern="Scale10000")` returned zero candidates and “No unused code found,” although that class existed and was unreferenced. The response did not disclose scan truncation. The score cache and SARIF consumers share the underlying limited candidate population.

The live governor scan reads only the first 20,000 source nodes per label. A SOQL-in-loop edge on method 20,001 was missed and the live scan returned an empty list. A fresh populated cache can cover more methods, but an absent or stale cache exposes this path, and cache-population paths have their own fixed limits.

**Fix:** paginate scans to completion or apply user filters before a declared cap. Carry scanned/total counts and an explicit incomplete state through live scans, caches, MCP text, and SARIF. Distinguish no findings in a complete scan from no findings in the inspected subset. Add tests above each limit, including a matching item immediately after it.

## Security, correctness, and delivery findings

### F05 — P2: the web explorer executes third-party CDN code inside the local graph application

**Evidence:** [app.js:13](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/web/public/app.js#L13), [index.html:9](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/web/public/index.html#L9), [README privacy claim:18](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/README.md#L18).

The explorer imports its visualization libraries from `esm.sh` and fonts from Google. The JavaScript dependencies are not part of the repository's lockfile/audit result. A remote module executes in the importing page's application context and can call the graph API as the page does. Thus Host/Origin checks do not isolate graph data from that code. The application also needs a network connection for a first uncached load.

This is a trust-boundary and claim problem, not observed source exfiltration. I did not observe the current libraries sending graph data out.

**Fix:** bundle the visualization dependencies and fonts locally, lock/audit their transitive dependencies, and add an appropriate CSP and an offline browser-network test. Restrict the unconditional “nothing leaves your machine” wording to what has actually been verified.

### F06 — P2: dead-code reports overstate what zero incoming graph edges prove

**Evidence:** [dead-code tool wording:95](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/mcp-server/src/tools/dead_code_audit.ts#L95), [deletion follow-up:139](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/mcp-server/src/tools/dead_code_audit.ts#L139), [age-based scoring:379](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/analyze/dead-code.ts#L379).

A parsed `@RestResource` class with an `@HttpGet` method was classified `dead`. This is a legitimate zero-inbound candidate, since external clients are not graph nodes. However, the MCP title is “Code nothing uses,” and the next step says to use `trace_upstream` to confirm nothing uses it before deletion. That traversal cannot establish the absence of external clients. Confidence is derived largely from age, so an old active endpoint can get a high-confidence score.

The SARIF rule catalog does acknowledge external entry points; this caveat is not consistently carried into the principal tool result. The shipped skill also asks for uncertainty, but clients can call the tool without that skill.

**Fix:** say “no captured incoming references,” mark known REST/global/scheduled/platform entry points separately, and require evidence outside the same graph for deletion confidence. Keep age as a separate signal. Preserve the external-use caveat in tool text and exported findings.

### F07 — P2: two advertised governor checks do not operate on normal parser output

**Evidence:** [populate.ts:162](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/analyze/populate.ts#L162), [edge-path exclusion:127](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/analyze/populate.ts#L127), [governor tool description](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/mcp-server/src/tools/governor_risk_check.ts#L125).

The source scanner for `unbounded_query` and `no_bulk` reads node attributes named `source` or `body`. Normal Apex parsing stores code as snippets rather than those attributes. The graph-only scanner detects direct in-loop operations and dynamic query attributes, but does not implement those two checks; the cached edge path deliberately omits unbounded queries too.

A normally parsed `return [SELECT Id FROM Account];` produced a complete SOQL edge, yet both `findGovernorRisks` and the populated risk table were empty. The raw-body code path exists, but that does not establish delivery through normal filesystem or live ingestion.

**Fix:** implement the advertised checks using parser facts or stored snippets, calibrate them with realistic positive/negative examples, or remove them from the advertised supported set. Share one detection implementation between cached and live answers to prevent drift.

### F08 — P2: dependency scans are not clean; distinguish installed packages from reachable vulnerabilities

**Evidence:** saved full and production-only `pnpm audit --json` outputs; [dependency declarations and overrides](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/package.json#L20). These are point-in-time registry results from this audit.

| Scope | Critical | High | Moderate | Low |
|---|---:|---:|---:|---:|
| All workspace dependencies, scanner summary | 4 | 26 | 25 | 8 |
| Production dependency graph, scanner summary | 0 | 3 | 9 | 4 |

These summary counts are affected dependency findings, not a count of independently exploitable application bugs. The production output contains 15 distinct advisory URLs; its three high entries come from two advisories affecting three installed version instances.

Relevant high findings include Zod `3.25.76` and `4.4.3`, and `body-parser` `2.3.0` through the MCP SDK's Express dependency. The Zod advisory concerns memory exhaustion while validating oversized collections. MCP input schemas use Zod, so collection and transport limits deserve explicit review; no destructive OOM payload was run. The current server uses stdio and the web explorer uses Node HTTP directly, so I did not find a current application path using body-parser's affected HTTP middleware. See the [Zod advisory](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) and [body-parser maintainer advisory](https://github.com/expressjs/body-parser/security/advisories/GHSA-27r3-jxmh-p828).

The development graph includes critical advisories for Vitest, tinypool, and a DOMPurify dependency of the Mermaid CLI. For example, the [Vitest maintainer advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-5xrq-8626-4rwp) requires its UI/API/browser exposure conditions; ordinary `vitest run` is not proof of that exposure.

**Fix:** update affected direct and transitive dependencies with compatibility checks; bound input size independently of schema validation; add dependency scanning and a documented reachability/exception policy to CI. Re-audit an installed published package too: monorepo-root pnpm overrides are absent from the published core manifest and do not constrain consumers' installations.

### F09 — P2: shipped SARIF security guidance conflates sharing with CRUD/FLS bypass

**Evidence:** [findings.ts:124](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/analyze/findings.ts#L124), [security classifier](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/analyze/security.ts#L112).

The rule description states that full access via OWD/sharing bypasses FLS and CRUD, and its short description equates sharing with Modify All/View All. Those are different security mechanisms. The analyzer also places every sharing rule with `Edit` access in the `sharingFullAccess` bucket, without evaluating whether the audience is broad or the grant is inappropriate.

[Salesforce's sharing documentation](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-security-sharing-rules.html) distinguishes record sharing from object and field permissions. An Edit sharing rule is not evidence of a CRUD/FLS bypass.

**Fix:** describe observed record-level access and the rule's audience, distinguish Edit from All, and reserve bypass/Modify All terminology for the actual permission facts. Keep unsupported OWD/user-effective-access analysis out of the asserted result.

### F10 — P2: field-security analysis loses case-insensitive identity in JavaScript

**Evidence:** [security.ts:134](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/analyze/security.ts#L134), [gap test:170](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/analyze/security.ts#L170). Independently reproduced.

The store can resolve a field without case sensitivity, but `fieldAccessMatrix` uses exact strings. A grant edge to `CustomField:account.secret__c` and a field node `CustomField:Account.Secret__c` produced both a grant matrix entry and an FLS-gap finding for the same logical field.

**Fix:** normalize comparison keys consistently in matrix construction and filtering, while retaining a canonical display name. Test mixed-case grant targets, definitions, and object filters. This is the same broad consistency concern as F02, in a separate consumer.

### F11 — P2: “Render entire org” silently omits stored metadata families

**Evidence:** [api.ts:265](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/web/src/api.ts#L265). Independently reproduced.

`fullGraph` enumerates a hardcoded label list rather than the graph's registered labels. It leaves out OmniScript, DataRaptor, IntegrationProcedure, native OmniStudio labels, and other stored types. A five-node graph containing an OmniScript returned four nodes and `truncated: false`, even with a limit of 100.

**Fix:** enumerate the actual stored labels and report all exclusions separately from the node-count limit. Derive UI label choices from the same source rather than maintaining several overlapping hardcoded lists.

### F12 — P2: capped schema responses contain edges to nodes absent from the response

**Evidence:** [api.ts:333](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/web/src/api.ts#L333), [edge append:380](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/web/src/api.ts#L380). Independently reproduced.

When `addNode` refuses another node at the schema cap, the caller still appends its edge. With one object, three consumers, and a limit of two nodes, the response contained two nodes and three edges, including two edges whose source node was absent. This is an invalid graph payload for a visualization that expects link endpoints in its node list. The payload defect was observed; browser rendering was not independently exercised.

**Fix:** append an edge only if both endpoint IDs exist in the final node set. Stop or explicitly count omitted neighbors when the cap is reached. Apply an endpoint-integrity assertion to every graph endpoint.

### F13 — P2: web search silently stops at 25,000 names after loading all names anyway

**Evidence:** [api.ts:117](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/web/src/api.ts#L117). Independently reproduced on a 50,000-node graph.

`search` calls `listAllQnames`, which materializes the whole graph's names, then checks only the first 25,000. An existing `Search49999` class was not found, and the API provides no incomplete-result indicator. The cap does not bound the initial database read/allocation it claims to protect.

**Fix:** push indexed text/prefix matching and limits into storage, with pagination or an explicit truncated flag. Use the existing search/storage capabilities where appropriate rather than a second partial in-memory search implementation.

### F14 — P2: enabling telemetry does not connect it to runtime events

**Evidence:** [telemetry enable:28](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/cli/src/commands/telemetry.ts#L28), [pipeline implementation](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/packages/core/src/telemetry/pipeline.ts), [privacy documentation](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/docs/PRIVACY.md).

The CLI writes configuration and creates a machine ID. Production source contains no creation of a `TelemetryPipeline` and no runtime event-recording calls from the CLI, ingestion pipeline, or MCP server. Config is read only by the telemetry-management commands. `LocalFileSink` is otherwise instantiated by the purge command, while preview sanitizes a fabricated event.

Thus the reusable primitives and unit tests exist, but the documented flow in which opt-in users receive sanitized runtime diagnostic events is not connected. Documentation also gives several conflicting telemetry file locations; code defaults to `<dataDir>/telemetry.jsonl`. The event schema admits successful CLI/tool events, so “failure-only” would need enforcement if collection is wired later.

**Fix:** either label this feature as scaffolding or implement explicit runtime wiring that honors consent and failure-only policy. Test enable → actual failure → sanitized persisted event → disable → no event. No remote telemetry sender was found.

### F15 — P2: native postinstall verification neither resolves nor opens the actual binding reliably

**Evidence:** [verify-native.mjs:52](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/apps/sfgraph/scripts/verify-native.mjs#L52), [signing walk:105](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/apps/sfgraph/scripts/verify-native.mjs#L105), and the saved installation log.

`tryLoad` resolves `better-sqlite3` from the wrapper package, which does not declare it directly. Frozen pnpm installation emitted “Cannot find module 'better-sqlite3'” even though core subsequently loaded it and all database tests passed. The signing walk stays under the wrapper package and skips symlinks, so it does not reliably reach pnpm's native dependency location.

Even when resolution succeeds, requiring better-sqlite3 only loads its JavaScript wrapper; the native binding is opened on `new Database(...)`. The separate CLI entry-point preflight already uses the correct dependency-resolution chain and instantiates a database, illustrating the implementation drift.

**Fix:** share the working resolution/probe logic, instantiate and close an in-memory DB, and locate actual native files from owning packages. Scope signing/rebuild actions to those files. Test pnpm's isolated dependency layout and an intentionally invalid binding, rather than a hoisted layout alone.

## Dead code, redundancy, and maintenance

### F16 — P3: the published core tarball contains orphan compiled code

The published `@ryanstark24/sfgraph-core@1.8.1` tarball includes `dist/parsers/vlocity/fallback.js`, exporting a zero-node `vlocityFallback`. No corresponding source exists in the audited tree or fresh build. All 204 matching JavaScript files compared byte-for-byte successfully; this is an additional artifact, not evidence that the normal compiled engine differs.

[The preflight check](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/scripts/preflight-publish.mjs#L454) compares the newest source and output timestamps. It cannot detect leftover outputs from deleted source files.

**Fix:** publish from a clean build directory and compare packed output to the clean build. Reject compiled paths whose source no longer exists. The observed orphan is unused; no active runtime failure was established from it.

### F17 — P3: dormant files and overlapping subsystems add unnecessary maintenance surfaces

Knip produced 92 file-level issue records, but that raw number is not a deletion list. Manual reference checks distinguish the following:

| Code | Assessment | Suggested action |
|---|---|---|
| `core/src/parsers/apex/visitor.ts` | Empty placeholder, no production references | Remove |
| `core/src/parsers/flow/element-visitors.ts` | Empty placeholder, traversal lives elsewhere | Remove |
| `core/src/extractors/live-org/extractors/generic-sobject.ts` | Implementation has no production caller | Remove or wire it deliberately; do not imply coverage from its presence |
| `core/src/extractors/live-org/reports.ts` | Exported `iterReports` always emits nothing; main ingestion uses generic metadata extraction | Deprecate/remove this misleading public surface, preserving real generic Report support |
| `core/src/parsers/worker-pool.ts` | Older exported Piscina wrapper; current ingestion uses `ingest/parse-pool.ts` and native worker threads | Deprecate/consolidate after checking external consumers |
| `models/src/loader.ts` vs `core/src/embedding/embed.ts` | Two loading paths with different policies; the former verifies vendored checksums, normal embedding uses the latter directly | Share model-location/integrity policy and document the supported loader |
| `analyze/populate.ts` vs `analyze/governor.ts` | Separate governor detectors already diverge, as F07 shows | Use one detector for live and cached results |
| `core/package.json` `zod-to-json-schema` | No production usage found in core; server has its own declaration/use | Remove the core declaration after dependency/build verification |
| `@types/jsforce` 1.x alongside jsforce 3.x | Legacy declaration package for a library that ships types | Check removal; replace untyped integration boundaries with current interfaces |

Do **not** delete the browser `public/app.js`, fixture JavaScript, public barrel exports, or dynamic-resolution dependencies just because Knip reports them. In particular, server `better-sqlite3` is used through `createRequire`, and wrapper/server package relationships require package-level resolution review. Bench helpers have no committed runner, so clarify ownership rather than declaring them product dead code automatically.

**Fix:** configure static analysis for browser entry points, fixtures, dynamic dependencies, and public API boundaries. Require a short owner/deprecation decision for retained alternative implementations. Do not refactor the 2,360-line ingestion module or 2,938-line graph store indiscriminately; extract cohesive orchestration/storage responsibilities while preserving their recovery and concurrency contracts.

### F18 — P3: documentation and enforcement disagree in several review-critical places

Examples include:

- [The 1.8.1 claim ledger](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/docs/claims/1.8.1.md#L5) says these changes have no GitHub Actions verification; current CI and the three-platform successful run demonstrate otherwise.
- [TESTKIT.md](https://github.com/ryanStark24/sfgraph/blob/ad4afd088d87e2565eada89a9b58d62c21977fd4/TESTKIT.md#L29) still gives 848 tests as the current baseline; the observed total is 2,963.
- The Apex-parser environment table says non-regex values are reserved, while the implementation accepts `ast` and `both`.
- The case-sensitivity design document still describes a proposed storage change, although current storage implements NOCASE; remaining consumer bugs are a different, narrower problem.
- Lint/typecheck cover web `src`, while the 1,001-line browser application under `public/app.js` is outside those normal checks. Two API-focused web test files do not establish browser integration or offline correctness.

**Fix:** derive version/count/capability documentation where practical, explicitly state unsupported delivery paths, and bring the browser entry into lint and browser integration checks. Prefer capability assertions tied to end-to-end output over tests that only hold wording or registry membership constant.

## Positive controls and remaining limits

Controls observed in the source include strict TypeScript configuration, validated SQL identifiers, parameterized data queries, org-path validation, loopback defaults with Host/Origin rejection, a public-bind opt-in, SARIF export-path containment, ingestion locks, skipped-source/deletion guards, versioned cache handling, and bounded context reuse. The regression suite specifically exercises many prior failures. These are meaningful engineering investments.

The assessment combined repository-wide inventory/static searches, dependency and limited historical secret scans, package/artifact inspection, full available tests, targeted review of trust boundaries and analysis/ingestion/storage paths, and independent reproductions. It is not a claim that every one of approximately 58,697 production TypeScript lines was manually proven correct. There were no applicable repository `AGENTS.md` files in the audited tree.

No real Salesforce authentication, retrieve/deploy, external-caller inventory, browser rendering session, large-org load test, or production penetration test was performed. No absence-of-vulnerability claim is made for unexercised paths. The zero historical token-pattern matches do not establish the absence of every secret format or previously revoked credential.

## Recommended remediation order

1. Repair the read-only boundary and case-safe manifest comparison. Add real-SDK transport and case-only manifest regressions.
2. Make live `auto` sync refresh actual content or fall back; disclose unsupported SourceMember types. Remove false-clean results from capped scans.
3. Correct security/dead-code wording and the supported governor check set. Make completeness and external entry points part of each result contract.
4. Bundle browser dependencies, fix graph endpoint integrity/label enumeration/search, and test the browser path.
5. Update/triage dependency advisories, wire or withdraw telemetry, and consolidate native-binding verification.
6. Publish from clean output, remove/deprecate dormant surfaces, and reconcile the claim ledger and documentation.

Acceptance should demonstrate changed behavior through normal CLI/MCP/browser entry points, not only through isolated helper tests. In particular: no unapproved SDK write reaches transport; a case-only diff emits no deletion; an auto sync changes the stored body/hash; a matching component after a former cap can be found; and a bounded result explicitly states any incomplete scope.
